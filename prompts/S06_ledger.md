# S06 · 크레딧 원장 (이중기입·홀드·성숙·회수)

| 항목 | 값 |
|---|---|
| 의존 | S03, S05 |
| 권장 모델 | Opus 5.5 (effort 최대) |
| 규모 | XL |
| 사람 필요 | 없음 |

이 차수는 `prompts/_PROTOCOL.md`를 따른다.

## 왜 중요한가
이 사업에서 크레딧은 장차 화폐가 되려는 것이다. 장부가 한 번이라도 틀리면 신뢰는 끝난다. 이 차수의 목표는 "동시에 수천 건이 몰려도, 재시도가 겹쳐도, 서버가 중간에 죽어도 **돈이 생기거나 사라지지 않는** 원장"이다. 깊게 생각하고, 속성 기반 테스트로 증명한다.

## 먼저 읽을 것

## 상세 요구사항

### 1. 계정과목
- 구매자 지갑(CR), 매장 미성숙 수익(CR), 매장 확정 수익(CR), 플랫폼 매출(CR), 플랫폼 검증 비용(CR), 홀드(CR), 외부 환전 정산(CR), 정산 처리 중(CR), 보류·조사(suspense, CR), 준비금(KRW), 외부 지출(KRW 또는 USD), 통화 변환 계정(통화별, 음수 허용), 테스트 충전 출처(KRW).
- 계정마다 음수 허용 여부를 정한다. 사용자 지갑은 절대 음수 불가.
- 준비금은 실제로 받은 통화(원화)로 기록한다. 달러 환산은 S08의 환율로 계산하며, 원장 안에서 통화를 섞지 않는다(통화 간 이동은 변환 계정을 거쳐 통화별로 각각 합 0).

### 2. 거래 종류 (각각 분개 규칙을 LEDGER.md에 표로)
1. `TEST_TOPUP` — 구매자가 원화를 냈다고 가정(테스트 결제). 준비금(KRW) 증가 + 구매자 지갑(CR) 증가. 환율·페그 값은 호출자(S08)가 계산해 넘긴다.
2. `JOB_HOLD` — 구매자 지갑 → 홀드(작업 최대 비용)
3. `JOB_CAPTURE` — 홀드 → 매장 미성숙 수익(노드 몫) + 플랫폼 매출(나머지) + 구매자 지갑(쓰고 남은 홀드 환불). 한 거래로.
4. `JOB_RELEASE` — 홀드 전액 → 구매자 지갑(작업 실패·취소)
5. `EARNING_MATURE` — 성숙 기간이 지난 미성숙 수익 → 확정 수익
6. `EARNING_CLAWBACK` — 부정 판정된 미성숙 수익 → suspense. 이어서 `REFUND`로 구매자에게 돌려줄 수 있다.
7. `VERIFICATION_COST` — 플랫폼이 부담하는 검증 작업 비용(플랫폼 비용 → 매장 미성숙 수익)
8. `EXTERNAL_EXCHANGE` — 구매자 지갑 → 외부 환전 정산(CR), 그리고 준비금(KRW) → 외부 지출(KRW). 실제 금액은 S16이 정산한다.
9. `MANUAL_PAYOUT_RECORD` — 매장 확정 수익 → 정산 처리 중. **실제 송금은 시스템 밖에서 운영자가 하고, 여기서는 기록만 한다.** 운영자 승인·참조번호·감사 필수.
10. `ADJUSTMENT` — 운영자 조정(사유 필수, 감사)
11. `REVERSAL` — 기존 거래를 부호를 뒤집어 상쇄(원 거래와 연결, 같은 거래를 두 번 되돌릴 수 없음)

### 3. API (모듈 내부 함수)
- `post(tx)`, `hold(buyer, amount, jobId, expiresAt)`, `capture(holdId, actualCost, split)`, `release(holdId)`, `matureDue(now)`, `clawback(earningId, reason)`, `refund(...)`, `recordManualPayout(...)`, `adjust(...)`, `reverse(txId, reason)`, `balance(account)`, `statement(account, cursor)`.
- 모든 함수는 `idempotencyKey`를 받는다. 같은 키 재호출은 같은 결과를 돌려주고 두 번 기록하지 않는다.

### 4. 동시성과 일관성
- 잔액 행을 계정 ID 순서로 `SELECT ... FOR UPDATE` 잠근 뒤 posting과 잔액을 같은 트랜잭션에서 쓴다(교착 방지).
- 직렬화 실패(40001)와 교착(40P01)은 지수 백오프로 제한 횟수만큼 재시도.
- 홀드 만료: 만료된 active 홀드는 주기 작업이 `release` 한다(작업 상태와 경합 시 한쪽만 이긴다 — 테스트로 증명).

### 5. 대사(reconciliation)
- 주기적으로: 잔액 = posting 합, 거래별 통화 합 = 0, 홀드 계정 잔액 = active 홀드 합, 미성숙 수익 계정 잔액 = pending earnings 합.
- 차이가 하나라도 있으면: 결과 기록, 경보용 지표, 그리고 **외부 환전·성숙 처리 자동 정지**(기능 플래그 `ledger_frozen`) — 사람이 확인하기 전까지 돈이 더 움직이지 않게(fail-safe).

### 6. 속성 기반 테스트 (fast-check + 실제 Postgres)
- 무작위 작업 순서(충전, 홀드, 캡처, 해제, 성숙, 회수, 환불, 조정, 되돌리기)를 여러 워커가 동시에 실행.
- 불변식: 통화별 합 0 / 잔액 = posting 합 / 비허용 계정 음수 없음 / 홀드 계정 = active 홀드 합 / 같은 멱등 키 재실행이 잔액을 바꾸지 않음 / 되돌리기가 정확히 원상 복구.
- 최소 10,000개 연산, 시드 고정으로 재현 가능. 실패 시 축소된 반례를 출력.

## 하지 말 것
- 출금(현금 인출) 함수 — 만들지 않는다
- 가격 계산·환율(S08), 외부 환전 실제 처리(S16)
- 원장 모듈 밖에서 잔액 테이블 직접 수정(린트·검사로 막는다: `account_balances`를 쓰는 SQL은 ledger 폴더에만 존재)

## 수용 기준
1. `pnpm verify` 통과
2. 속성 테스트 10,000+ 연산, 동시 워커 8개 이상에서 모든 불변식 유지
3. 경합 테스트: 같은 홀드에 캡처와 만료 해제가 동시에 → 정확히 하나만 반영
4. 대사 테스트: 일부러 잔액을 어긋나게 만든 DB에서 대사가 차이를 찾고 `ledger_frozen`을 켠다
5. 처리량 측정값(초당 캡처 거래 수)을 REPORT에 기록. 목표 ≥ 200건/초(단일 인스턴스, 개발 PC), 미달 시 원인과 개선안
6. `docs/LEDGER.md` 분개 규칙 표가 테스트와 일치(규칙 표에서 테스트 케이스를 생성하거나 표의 예시를 테스트로 검증)

## 적대적 검토 포인트
