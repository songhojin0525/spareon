## 목표
혼자 운영하는 사람이 자고 있어도 큰 문제는 알림으로 깨우고, 일어나서 무엇을 해야 할지 런북만 보고 따라 할 수 있게 한다. 데이터는 매일 백업되고, 복구가 실제로 된다는 것을 시험으로 증명한다.

## 먼저 읽을 것
- `docs/MVP.md`(SLO), `docs/E2E_REPORT.md`, `docs/SECURITY_REVIEW.md`, `docs/LEDGER.md`(대사), `docs/UPDATES.md`

## 산출물
- 서버 지표: Prometheus 형식 `/metrics`(별도 포트 또는 토큰 보호)
- `deploy/observability/` — Grafana 대시보드 JSON(노드·작업·돈·검증·에이전트 건강), Prometheus 알림 규칙 YAML
- `docs/runbooks/*.md` — 상황별 대응서(한국어, 단계별, 실제 명령)
- `scripts/backup.mjs`, `scripts/restore.mjs` + 복구 훈련 테스트
- `docs/OPERATIONS.md` — 매일·매주 할 일, 대시보드 보는 법

## 상세 요구사항

### 1. 지표 (이름은 `binjari_` 접두사, 낮은 카디널리티 — 노드 ID를 라벨로 쓰지 않는다)
- 노드: 매장별 연결 수, 상태별 수, 재연결률, 에이전트 버전 분포
- 작업: 종류·결과별 수, 대기열 길이, 대기 시간, 실행 시간, 선점 수, 이어쓰기 수, 선점 지연 히스토그램(에이전트 보고)
- 돈: 대사 차이(0이어야 함), 원장 동결 여부, 준비금 비율, 외부 지출, 가드 거부 수, 홀드 잔액
- 검증: 판정별 수, 격리 수, 회수액
- 시스템: API 지연, 에러율, DB 풀, WS 큐 길이
- 지표에 프롬프트·키·개인정보가 들어가지 않는지 테스트.

### 2. 알림 규칙 (임계값은 MVP SLO에서, 각 규칙에 런북 링크)
- 즉시: 원장 대사 차이 ≠ 0, 원장 동결, 준비금 비율 < 기준, 연결 노드 급감(30분 내 50% 감소), 서명·업데이트 실패 급증, 5xx 급증
- 근무 시간: 검증 실패 증가, 선점 지연 p95 악화, 디스크·DB 용량

### 3. 런북 (`docs/runbooks/`, 각각: 증상 → 확인 → 조치 → 복구 확인 → 사후 기록)
- `global-pause.md`(전체 멈춤과 해제), `bad-agent-release.md`(배포 롤백), `fraud-wave.md`(사기 노드 급증), `ledger-mismatch.md`(대사 차이 — 돈을 움직이지 말고 조사부터), `reserve-low.md`(준비금 경고), `db-restore.md`, `signing-key-compromise.md`, `server-down.md`, `store-complaint.md`(사장님이 "게임이 느려졌다"고 할 때)
- 런북의 명령이 실제로 존재하는지 검사하는 스크립트(package.json 스크립트·CLI 명령과 대조).

### 4. 백업과 복구
- `pg_dump` 기반 백업 → 압축 → 암호화(공개키 암호화 또는 대칭 키 — 키는 환경변수) → 보관 위치(로컬 폴더 / S3 호환) → 보존 정책(일 7개, 주 4개, 월 3개).
- 복구 훈련 테스트: 시드 데이터 DB 백업 → 새 DB에 복구 → 원장 대사 0 + 행 수 일치.
- 백업 성공·실패 지표와 알림.

## 하지 말 것
- 지표·로그에 개인정보·프롬프트
- 런북에 존재하지 않는 명령

## 수용 기준
1. `pnpm verify` 통과
2. 지표 엔드포인트 테스트(필수 지표 존재, 금지 라벨 없음)
3. 알림 규칙 검증(promtool이 있으면 사용, 없으면 YAML 스키마 검사 + REPORT 기록)
4. 백업 → 복구 훈련 테스트 통과
5. 런북 명령 존재 검사 통과, 런북 9개 완성

## 적대적 검토 포인트
- 알림이 너무 많아 무시하게 되는 구성(알림 피로)
- 백업 암호화 키를 백업과 같은 곳에 두는 실수
- 대사 차이 런북이 성급하게 돈을 움직이게 만드는 지시

## 선택 확장
- 외부 상태 확인(업타임 체크) 설정 가이드
- 주간 운영 보고서 자동 생성(지표 요약 마크다운)
