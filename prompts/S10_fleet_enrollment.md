## 목표
사장님이 매장을 만들고, PC에 에이전트를 설치하면 노드로 안전하게 등록되고, 매장 정책(운영 시간, 온도 한도 등)이 노드에 전달되며, 언제든 노드·매장·전체를 즉시 멈출 수 있게 한다. PC방 특유의 현실 — **모든 PC가 같은 이미지에서 복제되고, 재부팅하면 초기화되는 환경** — 을 처음부터 설계에 넣는다.

## 상세 요구사항

### 1. 매장과 정책
- 사장님은 매장을 만들고 수정한다(이름, 주소 메모, 전기요금 단가 원/kWh — 기본값은 BUSINESS_CONTEXT의 일반용 요금 + "직접 입력 권장" 표시).
- 정책은 S02 스키마를 그대로 쓴다: 주간 일정(30분 단위), 최소 유휴 분(기본 10분), 최대 GPU 온도(기본 80°C), 다운로드 허용 시간대(기본 02:00~10:00), 모델 허용 목록, 투명성 모드(손님에게 안내 표시 여부), 동시 작업 수(1).
- 정책은 버전 관리하고, 바뀌면 연결된 노드에 `config.update`로 전달할 수 있도록 이벤트를 낸다(전달은 S11).

### 2. 등록 코드
- 종류: `single`(PC 1대, 24시간 만료) · `image`(매장 단위, 여러 번 사용, 만료 길게, 언제든 폐기 가능 — 매장 마스터 이미지에 넣는 용도).
- 형식: 사람이 읽기 쉬운 8자(혼동 문자 제외 base32), 해시로 저장, 시도 횟수 제한.

### 3. 등록 흐름 (HTTPS, S02의 enroll 스키마)
1. `enroll.start`(코드) → 서버가 매장 확인 후 `storeSalt`와 일회용 nonce 반환
2. 에이전트가 ed25519 키쌍을 만들고, 하드웨어 지문 원본(GPU UUID 우선, 보조로 시스템 UUID — 일부 메인보드는 기본 UUID가 같으므로 GPU UUID를 1순위로)을 `HMAC(storeSalt, 원본)`으로 바꿔 전송. 원본은 서버로 보내지 않는다.
3. `enroll.complete`(공개키, 지문 HMAC, nonce 서명) → 노드 생성 또는 재부착:
   - `single` 코드: 새 노드
   - `image` 코드: 같은 매장에 같은 지문 HMAC의 노드가 있으면 **그 노드에 새 공개키를 다시 묶는다(재부착)** — 재부팅마다 초기화되는 PC가 매번 새 노드를 만들지 않도록. 재부착은 감사 기록, 속도 제한.
   - 사장님 설정에 따라 이미지 코드로 새로 생긴 노드는 자동 승인 또는 대시보드 승인 대기.

### 4. 복제 탐지
- 같은 노드 신원(공개키)으로 서로 다른 지문 HMAC이 등장하거나, 동시에 두 연결이 인증을 시도하면 → 두 쪽 다 격리(quarantine) + 재등록 요구 + 사장님·운영자에게 알림 이벤트.
- 같은 지문 HMAC이 서로 다른 매장에 동시에 등장하면 운영자 알림(PC 이동인지 부정인지 판단 필요).

### 5. 노드 상태와 기록
- 서버 측 상태: offline, idle(대기), customer(손님 사용 중), running(작업 중), paused, quarantined, disabled. 전이 규칙은 ARCHITECTURE의 상태 기계를 그대로 따른다(테스트로 강제).
- `presence_intervals` 기록 함수(입력은 S11에서 에이전트 status로 들어온다): 구간 겹침 없음, 시계 차이 보정.

### 6. 킬스위치
- 범위: 노드, 매장, 전체. 켜고 끄는 API, 감사 기록, 지속 저장(서버 재시작 후에도 유지).
- 켜진 범위의 노드에는 작업 제안 금지(S12가 확인) + 즉시 `control.pause` 전송 이벤트(S11이 전달).

### 7. API
- 사장님: 매장 CRUD, 정책 수정, 코드 발급·폐기, 노드 목록·이름 변경·비활성화, 승인 대기 노드 승인, 매장 일시정지.
- 운영자: 전체 조회, 격리·해제, 전체 킬스위치.

## 하지 말 것
- WebSocket 연결 처리(S11), 에이전트 쪽 코드(S17·S20)
- 하드웨어 지문 원본을 서버에 저장

## 수용 기준
1. `pnpm verify` 통과
2. 등록 테스트: 만료 코드, 재사용된 single 코드, 잘못된 서명, 폐기된 image 코드 → 모두 거부
3. 재부착 테스트: image 코드로 같은 지문이 재등록 → 노드 수 그대로, 공개키만 교체, 감사 기록
4. 복제 테스트: 같은 공개키 + 다른 지문 → 격리, 동시 인증 → 격리
5. 상태 전이 테스트(허용되지 않는 전이 거부), 정책 스키마 검증 테스트
6. 킬스위치 테스트: 켜면 지속 저장·감사·이벤트 발생, 서버 재시작 후 유지

## 적대적 검토 포인트
- 등록 코드 추측·재사용, 다른 매장 노드 가로채기
- 재부착 기능을 악용한 노드 탈취(지문 위조 가능성과 그 영향)
- 킬스위치가 조용히 실패하는 경로
