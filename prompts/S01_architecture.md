| 항목 | 값 |
|---|---|
| 의존 | S00 |
| 권장 모델 | Opus 5.5 (effort 최대) |
| 규모 | XL |
| 사람 필요 | 없음 |

이 차수는 `prompts/_PROTOCOL.md`를 따른다.

## 왜 중요한가
이후 31개 차수가 이 문서를 근거로 결정을 내린다. 여기서 놓친 실패 경로, 공격, 돈의 흐름은 나중에 몇 배 비싸게 돌아온다. 코드보다 생각이 많은 차수다. 서두르지 말고, 각 결정을 스스로 반박해 본 뒤 살아남은 것만 적는다.

## 먼저 읽을 것
- `docs/BUSINESS_CONTEXT.md` **전체** (이 차수만큼은 전체를 읽는다)
- `CLAUDE.md`, `prompts/STAGES.md`, 모든 차수 문서의 `목표`와 `수용 기준`(전체 그림을 잡기 위해 훑는다)

## 산출물

- `docs/THREAT_MODEL.md`
- `docs/MVP.md`
- `docs/GLOSSARY.md`

## 상세 요구사항

### 1. ARCHITECTURE.md
1. **시스템 맥락도**(mermaid): 사장님, 구매자, 운영자, PC방 PC(에이전트 + 런타임), 서버, DB, 아티팩트 저장소, 외부 모델 제공사, 웹.
2. **서버 모듈**과 책임, 의존 방향(순환 금지): auth, apiKeys, audit, ledger, pricing(peg·fx·reserve), registry(models·runtime·artifacts·tokenizer), fleet(stores·nodes·enrollment·policy·kill), gateway(ws), scheduler, metering, verification(reputation), buyerApi, batch, providers(external), reconciliation, retention, notifications.
3. **에이전트 모듈**: service, helper(세션), presence/policy, conn, executor, runtime(llama.cpp·ollama·fake), gpu, cache(LAN), update, identity, metrics.
4. **핵심 시나리오 시퀀스 10개**(mermaid sequenceDiagram):
   1. 매장 등록 → 설치 → 노드 등록(단일 코드 / 이미지 코드)
   2. 손님 없음 → 적격 → 작업 제안 → 수락 → 실행(스트리밍) → 완료 → 과금(홀드 → 캡처) → 수익 보류 → 성숙
   3. 손님 착석 → 선점 → 재배정(이어쓰기 포함)
   4. 구매자 스트리밍 호출 중 클라이언트 연결 끊김
   5. 배치 업로드 → 분할 → 진행 → 결과
   6. 외부 모델 환전 + 준비금 가드
   7. 검증(카나리아·중복·지문) → 판정 → 평판 → 격리·회수
   8. 에이전트 업데이트 단계적 배포 → 실패 → 자동 롤백
   9. 킬스위치(노드 / 매장 / 전체)
   10. 복원 솔루션 PC 재부팅 → 신원 재부착, 그리고 이미지 복제 충돌
5. **상태 기계**(mermaid stateDiagram) — 모든 전이와 그 전이를 일으키는 주체를 표기: 노드, 작업, 시도(attempt), 홀드, 수익(earning), 에이전트 릴리스.
6. **데이터 흐름과 보존**: 프롬프트·출력이 어디를 거치고, 어디에 얼마 동안 머무는지, 어디서 암호화되는지 표로.
7. **시간 예산 표**: 오퍼 수락 2초, 하트비트 5초, 리스 15초, 재개 창 10초, 선점 목표(손님 입력 → 프로세스 종료 0.5초, 입력 → VRAM 해제 p95 2초), 수익 성숙 기본 72시간 등. 값마다 근거, 서로 모순이 없는지 확인(예: 재개 창 < 리스), 조정 위치.
8. **규모 가정**: 초기 3매장 × 100대, 설계 목표 300매장 × 100대(동시 연결 3만). 병목과 확장 경로(단일 인스턴스 → 다중 인스턴스: LISTEN/NOTIFY, 연결 고정).
9. **자기 반박 절**: BUSINESS_CONTEXT의 가정 중 아키텍처에 영향을 주는 것 5개 이상을 골라 "이게 틀리면?"을 쓰고, 설계가 버티는지 또는 무엇을 바꿔야 하는지 쓴다.
10. **부록 — 차수별 책임 매핑 표**: 모듈·기능 → 담당 차수 ID.

### 2. THREAT_MODEL.md
- 보호 자산: 원장·준비금, 구매자 데이터(프롬프트·출력), 손님과 PC방 PC, 서명 키, 운영자 계정, 사장님 수익.
- 신뢰 경계 목록과 경계별 STRIDE 표.
- 공격자 프로필: 게으르거나 사기 치는 노드 운영자, 악성 구매자, PC를 만지는 손님, 복제 이미지, 외부 공격자, 탈취된 운영자 계정, 공급망(의존성·빌드·업데이트 채널).
- 각 위협 → 완화책 → 담당 차수 ID. 완화하지 않으면 '수용한 위험'과 이유.
- 위험도 상위 10개 순위와 근거.

### 3. ADR (각 문서: 맥락 / 결정 / 검토한 대안 / 결과와 트레이드오프 / 재검토 조건)
- 0002 Postgres를 작업 큐로 (`SKIP LOCKED`, `LISTEN/NOTIFY`)
- 0003 에이전트 프로토콜: WebSocket + JSON Schema 단일 원천
- 0004 추론 런타임: llama.cpp 고정 버전 + 개발용 Ollama
- 0005 돈은 정수 최소 단위 + 이중기입 원장
- 0006 크레딧은 화폐가 아니라 선불 연산 크레딧(법적 이유, 출금 기능 없음)
- 0007 검증 전략: 카나리아 + 서로 다른 매장 간 중복 실행 + 모델 지문 + 평판 + 성숙 기간 + 회수
- 0008 기기 신원: ed25519 챌린지 응답, 하드웨어 지문 HMAC, 이미지 재부착, 복제 탐지
- 0009 과금용 토큰 수는 서버가 센다(노드 보고값은 교차 검증용)
- 0010 데이터 보존과 프라이버시
- 0011 Windows 서비스 + 세션 헬퍼 구조(세션 0 격리, `GetLastInputInfo` 폴링, 저수준 키보드·마우스 훅을 쓰지 않는 이유 — 백신·안티치트 오탐과 사생활 인식)
- 0012 웹은 같은 출처 프록시(`/api/*` rewrite)
- 0013 발행 정책: 마켓플레이스 방식 기본, 발행형(난이도 조절)은 시뮬레이션 전용
- 0014 페그 모드: 달러 고정 기본, 바스켓은 실험 플래그
- 0015 업데이트: 서명 매니페스트 + 단계적 배포 + 자동 롤백
- 0016 손님 우선 원칙: 모든 불확실 상태의 기본값은 '멈춤'(fail-safe)

### 4. MVP.md
- v0.1 범위: 로드맵 0~1단계 완성 + 2단계 준비. 무엇이 들어가고 무엇이 플래그로 잠기는지.
- 명시적 비목표.
- SLO 표: 선점 지연(위 시간 예산), 작업 성공률 ≥ 99%(구매자 오류 제외, 시뮬레이션 기준), 원장 대사 차이 = 항상 0, API 오버헤드 p95 ≤ 300ms(추론 시간 제외), 킬스위치 전파 ≤ 1초(연결된 노드).
- "v0.1 완료"의 정의.

### 5. KNOWN_UNKNOWNS.md
- 모르는 것과 해소 방법(어느 차수, 자동/실기): 세션 0 서비스에서 CUDA 동작, 게임 안티치트와의 상호작용, PC방 복원 솔루션 동작, PC방 네트워크(방화벽·NAT·LAN 통신), GPU 간 그리디 출력 비결정성 정도, GPU별 tokens/s, 손님 없는 시간 분포, nvidia-smi 전력값 정확도, 백신 오탐(Go 바이너리는 오탐이 잦다).
- 항목마다 "가정이 틀렸을 때의 대안 설계".

### 6. `scripts/check-docs.mjs`
- 모든 `S\d\d` 참조가 STAGES.md에 존재하는지, ADR 링크가 실제 파일인지, mermaid 블록이 비어 있지 않은지, 위협 표의 모든 행에 완화(차수 ID) 또는 수용 사유가 있는지 검사. `pnpm verify`에 포함.

## 하지 말 것
- 기능 코드 구현(문서와 검사 스크립트만)
- BUSINESS_CONTEXT의 사업 결정을 뒤집기. 문제가 보이면 ARCHITECTURE의 '이견' 절에 근거와 함께 기록만 한다.

## 수용 기준
1. 산출물 전부 존재, `node scripts/check-docs.mjs` 통과, `pnpm verify` 통과
2. 시퀀스 10개·상태 기계 6개 존재, 모든 전이에 트리거 주체 표기
3. 위협 표의 모든 행에 완화(차수 ID) 또는 수용 사유
4. mermaid 문법 검증: 가능하면 mermaid 파서로 자동 검증, 불가하면 수동 검토 방법을 REPORT에 기록
5. 적대적 검토가 '돈이 새는 경로'와 '손님에게 영향이 가는 경로'를 찾도록 요청하고, 찾은 것이 문서에 반영됨

## 적대적 검토 포인트

- 시간 예산 사이의 모순
