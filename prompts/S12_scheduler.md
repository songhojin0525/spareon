## 왜 중요한가
작업이 사라지거나, 두 번 과금되거나, 손님이 앉았는데 GPU를 놓지 않으면 사업이 무너진다. 이 차수는 **손님이 언제든 끼어드는 불안정한 노드** 위에서 작업을 끝까지 완수하고, 정확히 한 번 과금하는 엔진을 만든다. 가상 시계 기반 결정적 시뮬레이션으로 증명한다.

## 상세 요구사항

### 1. 큐와 상태
- 작업 상태: queued → offered → running → completed | failed | canceled | expired. 시도(attempt) 상태는 별도. 전이는 ARCHITECTURE 상태 기계를 그대로 따르고, 허용되지 않는 전이는 DB 갱신 조건으로 막는다(`WHERE status = 'x'`로 조건부 갱신, 영향 행 수 확인).
- 큐에서 꺼낼 때 `FOR UPDATE SKIP LOCKED`. 새 작업·노드 상태 변화는 `LISTEN/NOTIFY`로 깨운다(폴링은 보조).

### 2. 매칭
- 하드 조건: 모델 호환(노드가 가진 모델 또는 준비 가능 + 매장 허용 목록), VRAM, 런타임 버전, 노드 상태 idle, 킬스위치·일시정지 아님, 매장 일정 안, 신뢰 노드 전용 요청이면 신뢰 노드만.
- 점수: 모델이 이미 로드됨 > 캐시됨 > 미보유 / 평판 / **안정성** / 매장 분산 / 최근 부하. 가중치는 설정값이고 문서화한다.
- **안정성 예측기**: 노드별 `presence_intervals`로 "지금부터 T분 동안 손님이 안 올 확률"을 요일·시간대별 경험적 생존 곡선으로 추정. 데이터가 적으면 매장 평균 → 전체 평균 순으로 기댄다(축소 추정). 대화형(스트리밍) 작업은 예상 소요 시간 동안 안정 확률이 높은 노드를 우선한다.
- 제안: `job.offer` → 2초 안에 수락 없으면 다음 후보. 거절 사유는 기록하고 매칭 점수에 반영.

### 3. 리스·선점·재배정
- 리스 15초, 하트비트로 연장. 만료되면 시도 실패 → 재배정.
- `job.preempted`(손님 착석 등) → 즉시 재배정(서버 쪽 처리 목표 1초 이내). 선점된 노드에 그 작업을 다시 주지 않는다(일정 시간).
- **이어쓰기(대화형)**: 스트리밍 중 선점되면, 지금까지 보낸 출력을 접두사로 다른 노드에 이어서 생성시킨다(`continuationPrefix`). 구매자는 끊김 없이 이어진 스트림을 받는다(지연은 생길 수 있음). 이어쓰기 횟수 상한, 상한 초과 시 명확한 에러로 종료.
- 재시도 예산: 작업당 최대 시도 3회(설정), 초과 시 실패 + 홀드 해제.

### 4. 우선순위·공정성·마감
- 대화형 > 배치 > 검증(검증은 별도 비율 보장, S13).
- 구매자 간 공정성: 결손 라운드로빈(DRR) — 한 구매자의 대량 배치가 다른 구매자를 굶기지 않게.
- 마감(deadline) 지난 작업은 만료 처리 + 홀드 해제.
- 구매자 취소·연결 끊김 → 진행 중 시도에 `job.cancel`, 이미 쓴 만큼만 과금할지(스트리밍) 정책을 정하고 문서화(기본: 실제 생성된 토큰만 과금).

### 5. 과금 (정확히 한 번)
- 작업 생성 시 S08 견적으로 홀드. 완료 시 **서버 토크나이저로 입력·출력 토큰을 다시 센 값**으로 비용 계산 → 캡처(노드 몫 → 매장 미성숙 수익, 성숙 시각 = 지금 + 성숙 기간). 실패·취소·만료 → 해제.
- 노드 보고 토큰 수와 서버 계산이 설정 비율(기본 5%) 넘게 다르면 검증 대상으로 표시(S13).
- 완료 메시지 중복·재전송·늦게 도착한 완료(이미 다른 노드가 끝낸 작업) → 과금은 첫 유효 완료 1번만. 늦게 끝낸 노드에는 정책에 따라 보상 없음(문서화).
- 원장 호출은 모두 멱등 키 사용(작업 ID + 단계).

### 6. 데이터 보존
- 입력·결과는 AES-256-GCM으로 암호화 저장(키 ID 포함, 키 교체 가능). 결과 전달 후 기본 24시간(배치는 결과 만료까지) 지나면 삭제 작업이 지운다. 삭제는 되돌릴 수 없으므로 설정값과 테스트로 확인.

### 7. 결정적 시뮬레이션
- 가상 노드 500개(시나리오별 손님 패턴: 저녁 붐빔, 새벽 한산, 무작위 착석), 작업 10,000개(대화형·배치 혼합), 무작위 선점·연결 끊김·느린 노드.
- 검사: 잃어버린 작업 0, 모든 홀드가 캡처 또는 해제로 끝남, 이중 캡처 0, 원장 대사 차이 0, 선점 후 재배정 지연 분포, 공정성 지표, 처리량.
- `SIM_REPORT.md`에 시나리오별 표.

## 수용 기준
1. `pnpm verify` 통과
2. 시뮬레이션 3개 시드에서 불변식 전부 유지(잃어버린 작업 0, 미해결 홀드 0, 이중 캡처 0, 대사 차이 0)
3. 선점 → 재배정 서버 처리 p95 ≤ 1초(시뮬레이션 기준)
4. 이어쓰기 테스트: 결정적 가짜 런타임에서 '중간에 선점된 출력 + 이어쓴 출력' = '끊김 없는 출력'
5. 공정성 테스트: 같은 가중치의 두 구매자가 처리량을 ±10% 이내로 나눠 가짐
6. 중복 완료·늦은 완료 테스트, 데이터 삭제 테스트
7. 성능 측정(작업 10,000개 시뮬레이션 소요 시간, 초당 배정 수) REPORT 기록

## 적대적 검토 포인트
- 상태 전이 경합(완료와 리스 만료가 동시에, 취소와 완료가 동시에)
- 굶주림(특정 모델·구매자·매장이 계속 밀림), 선점이 잦은 매장에 대화형 작업이 몰리는 문제
- 프롬프트가 평문으로 남는 곳(로그, 에러, 임시 변수 덤프)
