## 목표
"1크레딧이 무엇과 얼마에 바뀌는가"를 코드로 만든다: 버전이 있는 가격표, 작업별 가격 고정(견적), 노드 몫 계산, 환율, 페그 정책(달러 고정 기본, 바스켓 실험), 준비금 비율 가드와 일일 환전 한도. 이 사업의 진짜 핵심은 준비금 관리와 환율 설정이다(BUSINESS_CONTEXT 6절).

## 상세 요구사항

### 1. 가격표
- `price_versions`(초안 / 활성 / 보관) + `price_entries`(모델별 입력·출력 100만 토큰당 µCR, 노드 몫 bps, 외부 모델은 제공사 원가 µUSD).
- 작업 생성 시 활성 가격 버전 ID를 작업에 고정한다. 가격이 도중에 바뀌어도 그 작업은 고정된 버전으로 계산한다.
- 비용 = `ceil((tokensIn × inPrice + tokensOut × outPrice) / 1,000,000)` µCR — 반올림은 한 번만, 항상 올림(플랫폼이 손해 보지 않게, 그러나 구매자에게 표시). 정수 연산만.
- 노드 몫 = `floor(cost × payoutBps / 10,000)`, 플랫폼 몫 = cost − 노드 몫(합이 정확히 cost가 되게).
- 기본값은 `tools/econ-sim/params/defaults.json`에서 읽고, 없으면 안전한 하드코딩 기본값 + 경고.

### 2. 홀드 금액(견적)
- 작업 최대 비용 = 입력 토큰 수(서버 토크나이저로 계산, S09 전이면 보수적 추정 + `SKELETON(S09)`) × 입력가 + `max_tokens` × 출력가. 홀드는 이 금액, 캡처는 실제 사용량.

### 3. 환율과 페그
- `fx_rates`: 'USD/KRW' 등, 정수 마이크로 단위, 출처, 적용 시각. 운영자가 CLI/API로 입력(자동 수집은 범위 밖).
- **환율 노후 가드**: 최신 환율이 설정 기간(기본 7일)보다 오래되면 외부 환전과 테스트 충전을 막고 명확한 에러 코드(`fx_stale`)를 돌려준다.
- `PegPolicy` 인터페이스:
  - `UsdFixed`(기본): 1 CR = 설정값 µUSD(기본 1,000,000 = 1달러).
  - `Basket`(실험, 플래그로 잠금): 참조 모델들의 가격 지수로 1 CR의 가치를 매일 스냅숏. 스냅숏은 저장·감사.
- 원화 충전 → 크레딧: 원화 ÷ 환율 ÷ 페그, 정수 연산, 반올림 방향 명시(구매자에게 불리하지 않게 내림 + 차액 표시).

### 4. 준비금 가드 (뱅크런 방지)
- 부채 = 유통 중인 구매자 크레딧(지갑 + 홀드)의 달러 환산. 준비금 = 준비금 계정(KRW)의 달러 환산.
- 외부 모델 환전 요청 시: `환전 후 준비금 / 부채 ≥ reserveMinRatio`(기본 1.0 — econ-sim 추천값 우선)이고 사용자·전체 일일 한도 이내일 때만 허용. 아니면 `reserve_guard` 또는 `daily_cap` 에러.
- 판정과 차감은 경합 없이 원자적으로(동시 요청 1,000건이 와도 비율이 기준 아래로 내려가지 않게).
- 원장 `ledger_frozen` 플래그가 켜져 있으면 무조건 거부.

### 5. 조회 API
- 구매자용: 모델별 가격, 1크레딧으로 쓸 수 있는 양(환율표 — BUSINESS_CONTEXT 3절의 표 형식), 내 일일 한도 잔여.
- 운영자용: 준비금 비율, 부채, 오늘 환전량, 가드 거부 횟수.

## 하지 말 것
- 실제 결제 연동, 환율 자동 수집, 외부 제공사 호출(S16)
- 부동소수점 사용(환율·지수도 정수 마이크로 단위)

## 수용 기준
1. `pnpm verify` 통과
2. 비용·분배 속성 테스트: 임의 토큰 수·가격에 대해 노드 몫 + 플랫폼 몫 = cost, cost ≤ 홀드
3. 가격 변경 경합 테스트: 작업 도중 가격표가 바뀌어도 고정된 버전으로 과금
4. 뱅크런 테스트: 동시 환전 요청 1,000건 → 비율이 기준 미만으로 내려가지 않고, 원장 불변식 유지
5. 환율 노후 테스트, 페그 두 모드의 계산 테스트(바스켓은 플래그 꺼짐 상태에서 접근 거부 포함)
6. `docs/PRICING.md`의 예시 숫자가 테스트로 검증됨

## 적대적 검토 포인트
- 반올림 방향 실수로 쌓이는 차액, 0토큰·초대형 입력 같은 경계값
- 가드 판정과 차감 사이의 경합(TOCTOU)
- 운영자 실수로 가격이 0이나 터무니없는 값이 되는 경우(상·하한 검증, 활성화 전 확인 단계)
