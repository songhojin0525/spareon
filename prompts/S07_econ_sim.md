# S07 · 경제 시뮬레이터·기본값 추천

| 항목 | 값 |
|---|---|
| 의존 | S01, S06 |
| 권장 모델 | Opus 5.5 (effort 최대) |
| 규모 | XL |
| 사람 필요 | 없음 |

이 차수는 `prompts/_PROTOCOL.md`를 따른다.

## 왜 중요한가
PC방 몫 비율, 준비금 비율, 성숙 기간, 검증 비율, 가격 — 이 숫자들이 사업의 생사를 가른다. 지금은 대부분 가정이다. 이 차수는 가정을 **명시하고, 범위로 다루고, 어떤 가정이 결과를 가장 크게 흔드는지** 보여 주는 시뮬레이터를 만들어, 코드의 기본값을 근거 있게 정한다. 창업자가 사장님께 "얼마 벌 수 있다"고 말할 때 정직한 범위를 주는 도구이기도 하다.

## 먼저 읽을 것
- `docs/BUSINESS_CONTEXT.md` 전체(특히 5·6·7·8·10절의 숫자와 출처), ADR 0013·0014, `docs/LEDGER.md`

## 산출물
- `tools/econ-sim/` (TypeScript, 순수 함수 + 시드 고정 난수, 외부 서비스 호출 없음)
- `tools/econ-sim/params/assumptions.json` — 모든 입력값: 값(또는 범위·분포), 단위, 출처 URL·날짜 또는 "가정", 어느 실측으로 교체할지
- `tools/econ-sim/params/defaults.json` — S08 등이 읽어 쓸 **추천 기본값**(근거 포함)
- `docs/ECONOMICS_REPORT.md` — 한국어 보고서(표, 차트, 결론, 한계)
- 차트(SVG) — `docs/economics/*.svg`

## 상세 요구사항

### 1. 모델
- **공급**: 매장 수, 매장당 PC 수(70~100), GPU 구성(RTX 4060/4070 등 비율), 시간대별 손님 없는 확률(요일 × 시간 프로필 3종: 보수적·보통·낙관적 — 근거가 없으면 '가정'으로 넓게), 처리량(tokens/s, GPU × 모델) — **공개 벤치마크를 찾을 수 있으면 출처와 함께, 없으면 넓은 범위로 두고 S19 실측으로 교체 표시**. 이 차수에서 처리량 숫자를 지어내지 않는다.
- **비용**: 전력(GPU별 kW 가정), 한전 일반용 전력량요금(계절별 91.9 / 119.0 / 132.4 원/kWh — 기본요금은 매장이 이미 내므로 증분 비용에서 제외하고 그 판단을 문서화), 검증 오버헤드(중복 실행 비율 × 작업 비용), 플랫폼 고정비(서버·DB, 범위).
- **수요**: 구매자 세그먼트(대량 배치 / 대화형), 시간대별 수요, 가격 민감도(경쟁 가격 대비) — 경쟁 기준점: Vast.ai 4060 $0.08/h, 4070 $0.136/h, Salad 4060 $0.05/h, 오픈소스 모델 API 시장 가격(조사 가능하면 출처와 함께).
- **돈의 흐름**: 판매 단가(100만 토큰당), PC방 몫 비율(bps), 성숙 기간에 따른 현금 흐름, 회수율, 외부 모델 환전 마진, 준비금.
- **페그**: 달러 고정 vs 바스켓 — 외부 모델 가격이 매년 하락하는 시나리오(-30%, -50%/년)에서 보유자의 구매력과 플랫폼 부채 변화.
- **발행형 실험(시뮬레이션 전용)**: 비트코인식 난이도 조절 — 목표 발행 속도를 유지하도록 '1크레딧당 필요한 일의 양'을 주기마다 조정. 연산 효율 향상 시나리오에서 인플레이션·디플레이션 결과. 결론: 마켓플레이스 방식 유지 여부에 대한 근거.

### 2. 시나리오
- 규모: S1 파일럿(1매장 80대), S2 10매장, S3 100매장
- 스트레스: 뱅크런(하루 안에 크레딧의 X%가 외부 모델 환전 요청), 외부 모델 가격 급락, 경쟁사 가격 인하, 낮은 가동률(10%), 부정 노드 5%, 겨울 전기요금, 손님 없는 시간이 가정의 절반
- 각 시나리오는 몬테카를로(시드 고정, 반복 N회)로 분포(중앙값, 10~90 백분위)를 낸다.

### 3. 출력
- 핵심 표: PC 1대·매장 1곳 월 수익(사장님 몫, 전기요금 차감 후), 플랫폼 월 마진, 손익분기 매장 수, 준비금 최저 비율, 뱅크런 생존 여부.
- 민감도 분석: 각 가정을 ±범위로 흔들었을 때 '사장님 월 수익'과 '플랫폼 마진'의 변화(토네이도 차트). **가장 영향이 큰 가정 3개를 보고서 맨 앞에.** 이것이 파일럿에서 가장 먼저 측정할 것이다.
- 추천 기본값(`defaults.json`): `nodePayoutBps`, `reserveMinRatio`, `dailyExchangeCapPerUser`, `dailyExchangeCapGlobal`, `maturationHours`, `redundancySampleRate`, `canaryPerNodePerDay`, 오픈소스 모델 기본 가격 — 각 값에 이유와 민감도.
- 사장님 안내용 "정직한 범위" 문장 초안(측정 전임을 명시).
- 차트는 Vega-Lite를 Node에서 SVG로 렌더링하는 방식 권장(헤드리스, 브라우저 불필요). 불가하면 직접 SVG 생성.

### 4. 검증
- 단위 테스트: BUSINESS_CONTEXT 7절 예시(4060: 시간당 약 79~89원, 매장 월 152만~171만 원)를 같은 가정으로 재현.
- 결정성: 같은 시드 → 같은 출력(출력 해시 비교 테스트).
- 보존 법칙: 시뮬레이션 내 돈의 총합(구매자 지불 = 사장님 몫 + 플랫폼 몫 + 환불 + 보류 잔액)이 맞는지 매 단계 검사.

## 하지 말 것
- 출처 없는 숫자를 사실처럼 쓰기 — 모든 입력은 출처 또는 '가정' 표시
- 서버 코드 변경(이 차수는 도구와 문서)

## 수용 기준
1. `pnpm verify` 통과
2. `pnpm --filter @binjari/econ-sim run all`이 보고서와 차트를 다시 만든다(같은 시드면 바이트 동일)
3. 예시 재현 테스트와 보존 법칙 테스트 통과
4. `assumptions.json`의 모든 항목에 출처 또는 '가정' + 교체 계획
5. 보고서 맨 앞에 "가장 영향이 큰 가정 3개"와 "추천 기본값 표"가 있다

## 적대적 검토 포인트
- 낙관 편향(수요·가동률·가격을 좋게만 가정)
- 단위 실수(시간·kWh·달러·원, µCR)
- 시뮬레이션 안의 돈 보존 위반, 결과를 실제보다 확실하게 쓰는 문장

## 선택 확장
- CSV로 가정 바꿔 넣고 다시 돌리는 간단한 CLI 마법사
- 파일럿 실측값(S31 내보내기 형식)을 입력받아 가정을 갱신하는 경로
