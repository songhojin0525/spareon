# S11 · 에이전트 게이트웨이 (WebSocket)

| 항목 | 값 |
|---|---|
| 의존 | S10 |
| 권장 모델 | Opus 5.5 |
| 규모 | L |
| 사람 필요 | 없음 |

이 차수는 `prompts/_PROTOCOL.md`를 따른다.

## 목표
수천 대 PC가 동시에 붙는 WebSocket 관문을 만든다: 기기 키로 인증하고, 모든 메시지를 스키마로 검증하고, 상태를 받아 기록하고, 서버의 명령(작업 제안, 취소, 일시정지, 설정, 모델 준비, 업데이트)을 확실히 전달한다. 연결이 끊기고 다시 붙는 것이 일상인 환경을 전제로 한다.

## 먼저 읽을 것
- `docs/PROTOCOL.md` 전체, ADR 0003·0008, `docs/ENROLLMENT.md`, `docs/ARCHITECTURE.md`(시간 예산, 규모 가정)

## 산출물
- `apps/server/src/gateway/` — WS 엔드포인트, 인증, 세션, 메시지 라우팅, 명령 전달·확인 추적, 상태 수집
- `packages/testkit`의 `FakeAgent` 확장 — 스크립트로 행동을 지정(느린 수락, 작업 중 끊김, 잘못된 메시지, 오래된 nonce 재사용 등)
- `docs/GATEWAY.md` — 연결 수명주기, 재연결·재개 규칙, 확장 방식, 한도
- S04의 `SKELETON(S11)`(개발용 공유 비밀 인증) 제거 — 개발 모드 플래그에서만 남기고 운영에서는 시작 거부

## 상세 요구사항

### 1. 인증
- 연결 직후 `hello` → `auth.challenge`(일회용 nonce, 짧은 만료) → `auth.prove`(S02 서명 규칙) → `auth.ok` / `auth.fail`.
- 지원하지 않는 protocolHash, 비활성·격리 노드, 재사용된 nonce, 잘못된 서명 → `auth.fail` 후 연결 종료.
- 인증 전에는 `hello`와 `auth.prove`만 허용. 인증 시간 제한 5초.

### 2. 세션과 재개
- `auth.ok`에 `resumeToken`. 끊긴 뒤 재개 창(기본 10초, S01 시간 예산과 일치) 안에 다시 붙으면 진행 중 시도(attempt)를 유지하고, 창을 넘기면 진행 중 시도를 실패(재배정 대상)로 넘긴다(S12가 처리할 훅 호출).
- 같은 노드의 두 번째 연결은 S10 복제 탐지 규칙을 따른다(단, 재개 토큰을 가진 재연결은 정상 처리하고 이전 연결을 닫는다).

### 3. 메시지 처리
- 모든 수신 메시지를 S02 스키마로 검증. 실패하면 `error` 응답, 일정 횟수(기본 5회/분) 넘으면 연결 종료.
- 크기 제한(1 MiB), 연결당 메시지 속도 제한, 송신 큐 상한(넘치면 느린 연결 종료 — 서버 메모리 보호).
- `status` → 노드 상태·지표 갱신 + `presence_intervals` 기록(S10 함수). `heartbeat` → `heartbeat.ack`(서버 시각) + 시계 차이 기록.
- 작업 관련 메시지(`job.*`)는 스케줄러(S12)로 넘기는 인터페이스만 정의하고, 이 차수에서는 테스트용 구현으로 연결한다.

### 4. 명령 전달
- 서버 내부 API: `sendOffer`, `sendCancel`, `sendPause/Resume`, `sendKill`, `sendConfigUpdate`, `sendModelEnsure`, `sendUpdateAvailable`. 각 명령에 응답(ack) 대기·시간 제한·재전송 규칙.
- 킬스위치 이벤트(S10)를 받으면 해당 범위의 연결된 노드에 즉시 전송. **연결된 노드까지 1초 이내**가 목표.
- 정책 변경 이벤트 → `config.update`.

### 5. 다중 인스턴스 준비
- 기본은 단일 인스턴스. 다만 명령이 다른 인스턴스에 붙은 노드로 가야 할 때를 위해 Postgres `LISTEN/NOTIFY` 기반 팬아웃을 구현하고 테스트한다(두 서버 인스턴스 + 노드 분산 테스트).
- 종료 시 드레인: 새 연결 거절 → 노드에 재연결 안내 → 진행 중 작업은 설정 시간(기본 30초)까지 기다린 뒤 종료.

### 6. 부하 확인
- `FakeAgent` 1,000개 동시 연결·하트비트·상태 보고를 개발 PC에서 실행하고 CPU·메모리·지연을 기록한다(목표치보다 결과를 정직하게 기록하는 것이 중요).

## 하지 말 것
- 작업 배정 로직(S12), 검증(S13)
- 에이전트 코드(S17)

## 수용 기준
1. `pnpm verify` 통과
2. 인증 테스트: 재사용 nonce, 잘못된 서명, 격리 노드, 모르는 protocolHash → 모두 거부
3. 잘못된 메시지 반복 → 연결 종료, 크기 초과 → 종료, 하트비트 끊김 → 오프라인 처리 + 진행 중 시도 실패 훅 호출
4. 재개 창 안 재연결 → 세션 유지, 창 밖 → 시도 실패 처리
5. 킬스위치 전달 지연 측정(연결된 노드 100개에서 p95 ≤ 1초)
6. 두 인스턴스 팬아웃 테스트 통과, 1,000 연결 부하 측정값 REPORT 기록

## 적대적 검토 포인트
- 인증 전 메시지 처리, 리소스 고갈(느린 소비자, 연결 폭주)
- 재개 토큰 탈취·재사용, 복제 탐지와 재개 규칙의 충돌
- 명령이 전달됐다고 착각하는 경로(ack 없는 성공 처리)

## 선택 확장
- 연결별 진단 정보 운영자 API(마지막 메시지 시각, 지연, 큐 길이)
- 메시지 압축(permessage-deflate) 효과 측정
