## 핵심 설계 결정 (대안 → 선택 → 스스로 반박한 결과)

1. **시간 예산의 기준점은 '마지막으로 받은 메시지'로 통일한다.**
   - 문제: 재개 창 10초를 '끊김을 알아챈 시각'부터 세면, 반쯤 열린 연결(TCP 종료 신호 없음)에서는 끊김 감지가 늦어져 재개 창이 리스(15초)를 넘는다. 그러면 재개가 허용된 시도를 리스 만료가 이미 실패 처리하는 모순이 생긴다.
   - 선택: 재개 마감 = 마지막 수신 + 10초, 리스 만료 = 마지막 갱신(= 마지막 수신) + 15초. 그래서 `2 × 하트비트(10초) ≤ 재개 창(10초) < 리스(15초)`가 항상 성립한다. 5초 여유는 서버 처리·청소 작업 지연용이다.
   - 반박: "하트비트 한 번만 놓쳐도 재개 창 절반이 사라진다" → 맞다. 대신 에이전트도 같은 기준으로 '서버와 10초 넘게 연락이 끊기면 스스로 작업을 멈춘다'(fail-safe, 킬스위치를 못 받는 상태를 10초로 묶는다). 양쪽이 같은 시계 기준을 쓰므로 살아남는다.
2. **노드 상태는 S10 목록 + `pending`(승인 대기), '작업 가능 여부'는 상태가 아니라 속성(`eligible` + 사유 코드)으로.**
   - 대안: `ineligible` 상태 추가. 반박: 온도·일정·헬퍼 없음 같은 사유가 늘 때마다 상태가 늘어난다. 사장님 화면 칩(손님 사용 중 / AI 작업 중 / 대기)과도 안 맞는다. → `customer`는 손님이 있을 때만, 그 밖의 '작업 불가'는 `idle` + `eligible=false` + 사유.
3. **이어쓰기(선점 후 재배정) 시 노드 몫은 시도별로 구매자에게 실제 전달된 출력 토큰 수에 비례해 나눈다(정수, 최대 나머지 방식).**
   - 대안 A: 완료한 노드가 전부. 반박: 선점당한 매장이 한 일이 사라진다. 대안 B: 시간 비례. 반박: 노드가 시간을 부풀릴 수 있다. → 서버가 센 '전달된 토큰'만 근거로 쓴다(조작 불가). 비스트리밍 작업의 선점된 시도는 출력이 버려지므로 몫 0(가정으로 기록).
4. **준비금 부채에 매장 수익(미성숙·확정·정산 처리 중)도 넣는다(S08 명세 보완 — 이견 절에 기록).**
   - S08 명세는 부채를 '구매자 크레딧(지갑+홀드)'만으로 정의한다. 캡처가 일어나면 구매자 부채는 줄지만 사장님에게 현금으로 줄 의무가 생긴다. 이걸 빼면 가드가 준비금을 '남는 돈'으로 보고 외부 환전에 써 버려, 사장님 정산금이 사라지는 돈 구멍이 생긴다.
5. **셀프 서비스 테스트 충전은 별도 통화 `TCR`(샌드박스 크레딧)로 분리한다(S06·S25 보완 — 이견 절).**
   - 문제: 구매자가 무료 테스트 충전으로 만든 크레딧으로 자기(또는 공모한) 매장에 작업을 주면, 매장 수익이 쌓이고 수동 현금 정산으로 진짜 돈이 나간다. 같은 크레딧이 실제 외부 API(유료) 지출의 근거가 될 수도 있다.
   - 선택: 운영자만 할 수 있는 `TEST_TOPUP`(창업자가 실제로 낸 돈을 기록, 파일럿용)은 CR, 구매자 셀프 충전은 TCR. TCR로 결제된 작업의 매장 수익은 TCR로 쌓여 정산 불가, TCR로는 실제 외부 호출 불가(모의만). 원장은 이미 통화별 합 0을 강제하므로 통화 하나를 더하는 비용이 작다.
   - 반박: "복잡도 증가" → 통화 코드 하나와 정산·환전 거부 규칙 두 개다. 돈이 새는 경로를 막는 이득이 크다.
6. **지문 HMAC은 두 개: 매장 솔트(재부착용) + 전역 솔트(매장 간 중복 탐지용).**
   - S10 명세는 `HMAC(storeSalt, 원본)` 하나로 재부착을 하면서 '같은 지문이 다른 매장에 동시에 나타나면 알림'도 요구한다. 매장마다 솔트가 다르면 매장 간 비교가 불가능하다(모순). → 두 값을 보낸다. GPU UUID는 128비트 난수라 전역 솔트가 공개돼도 원본을 역산할 수 없다.
7. **검증 작업이 일반 작업과 구별되지 않게: 오퍼에 '검증 플래그'를 넣지 않고, 모든 작업에 서버가 시드를 붙인다.**
   - S02 명세의 `job.offer`에 `verification 플래그`가 있다. 이 플래그는 게으른 노드에게 "이번만 성실하게 하라"고 알려 주는 셈이다(S13 '구별 불가' 요구와 모순). 또 중복 실행을 그리디 작업에만 하면 노드는 temperature 0 작업만 성실히 하고 나머지에서 속일 수 있다. → 플래그 제거, 모든 작업에 시드 부여, 중복 실행은 같은 파라미터·시드로 재실행. GPU 간 시드 샘플링 일치도는 미지수(KNOWN_UNKNOWNS)이므로 대안으로 '교사 강제(teacher-forced) 로그확률 검사'를 적어 둔다.
8. **에이전트 로컬 데드맨 스위치: 적격 판정 '임대'가 1초 넘게 갱신되지 않으면 감시 고루틴이 Job Object를 종료한다.**
   - 서비스 일부가 교착되면 선점 경로도 멈출 수 있다. 감시자는 잠금을 공유하지 않는 별도 경로로, '불확실 = 멈춤' 원칙(ADR 0016)을 프로세스 내부 고장에도 적용한다.
9. **스케일: v0.1은 단일 인스턴스. 리스 갱신은 메모리에서 하고 DB에는 5초마다 모아서 쓴다. 3만 연결 단계에서는 '인스턴스 생존 행 + 연결 고정'으로 바꾼다.**
   - 하트비트마다 DB에 쓰면 3만 노드에서 초당 6천 건 쓰기다. 관리형 Postgres 저가 티어로는 감당할 수 없다.
10. **문서 검사 확장은 의존성 없는 `check-docs.mjs`에, mermaid 문법은 실제 mermaid 파서(+jsdom)를 쓰는 repo-checks 테스트에 둔다.**
    - `check-docs.mjs`는 `pnpm install` 전에도 돌아야 하므로 의존성을 넣지 않는다(S00 결정). mermaid 파서는 무거우니 devDependency로 테스트에만 둔다. 실험으로 mermaid 11.17.2 `parse()`가 Node + jsdom에서 문법 오류를 잡는 것을 확인했다.

## check-docs 확장 규칙
1. 문서 안의 모든 `S\d\d` 참조가 `prompts/STAGES.md` 표에 있어야 한다(STAGES.md가 없으면 건너뜀 — 임시 폴더 테스트용).
2. 문서 안의 `ADR NNNN` 글 참조와 ADR 링크가 실제 `docs/adr/NNNN-*.md` 파일을 가리켜야 한다.
3. ```` ```mermaid ```` 블록은 비어 있으면 안 되고 닫혀 있어야 한다.
4. `docs/` 아래 `stateDiagram` 블록의 모든 전이(`A --> B`)에 `: [주체] 사건` 라벨이 있어야 하고, 주체는 정해진 어휘에 있어야 한다.
5. `docs/THREAT_MODEL.md`에서 `담당 차수` 열이 있는 표의 모든 행은 차수 ID(S\d\d) 또는 `수용: <사유>`를 가져야 한다. 위협 ID는 중복 금지.
6. CLI 실행 시 필수 산출물(ARCHITECTURE, THREAT_MODEL, MVP, GLOSSARY, KNOWN_UNKNOWNS, ADR 0002~0016)이 있어야 한다.
- 별도 repo-checks 테스트: 모든 mermaid 블록을 mermaid 파서로 파싱, ARCHITECTURE의 sequenceDiagram ≥ 10, stateDiagram ≥ 6.

## 위험
- 문서가 길어 서로 모순될 수 있다 → 시간 예산·상태 이름을 한 곳(ARCHITECTURE)에 두고 다른 문서는 링크만 한다. 적대적 검토에 모순 찾기를 명시적으로 요청한다.
- mermaid 파서가 vitest(ESM)에서 안 불릴 수 있다 → 실패하면 별도 Node 스크립트로 돌리는 테스트로 바꾼다.
- 이후 차수 명세와 다른 결정(이견) → BUSINESS_CONTEXT 사업 결정은 뒤집지 않는다. 기술 명세 보완은 ARCHITECTURE '이견' 절과 ADR에 근거와 함께 남기고, 해당 차수가 읽게 차수 매핑에 표시한다.
