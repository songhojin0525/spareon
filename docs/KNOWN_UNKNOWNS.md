# 알려진 미지수 (KNOWN_UNKNOWNS)

> 기준일 2026-10-09, 작성 차수 S01. 설계가 기대고 있지만 아직 확인하지 못한 사실들이다. 항목마다 '가정이 틀렸을 때의 대안 설계'를 미리 정해 두어, 실기·파일럿 결과가 나쁘게 나와도 설계를 처음부터 다시 하지 않게 한다.
> 해소 방법: **자동** = 코드·시뮬레이션·CI로 확인 · **실기** = Windows + GPU 실제 PC에서 사람이 확인(`docs/manual-tests/SNN.md`. 기준은 NVIDIA, 지금 가진 시험 PC는 AMD RX 5700 XT — ADR 0019) · **파일럿** = 실제 매장에서 측정(S31 이후) · **사람** = 계약·법률 등.
> 확인되면 그 항목에 결과·날짜·근거를 적고 '해소됨'으로 표시한다. 결과가 설계를 바꾸면 ARCHITECTURE·ADR도 같은 커밋에서 고친다.

## 1. 항목별 상세

### K1. 세션 0 서비스에서 CUDA가 동작하는가
- **왜 중요한가**: 런타임을 서비스 계정(세션 0)으로 띄워야 손님(사용자 권한)이 런타임 메모리를 읽거나 죽이지 못한다(THREAT_MODEL RT-01, RT-05). ADR 0011의 전제다.
- **현재 가정**: 세션 0에서도 NVIDIA CUDA 계산은 동작한다(그래픽 출력이 아니므로). 근거는 일반적인 서버용 GPU 서비스 사례이며, 소비자용 드라이버·Windows 10/11 PC방 환경에서는 확인 전이다.
- **해소**: 실기(S22 체크리스트) — 서비스 계정으로 `llama-server`를 띄워 GPU 오프로드가 되는지, 처리량이 사용자 세션과 같은지 비교. S19 bench 도구를 서비스 모드로 한 번 실행.
- **판정 기준**: GPU 레이어가 모두 올라가고 처리량 차이 10% 이내면 가정 유지.
- **틀리면**: 런타임을 사용자 세션에서 띄우되 (1) 손님 계정이 아닌 별도 저권한 로컬 계정으로 `CreateProcessAsUser`, (2) 선점 권한은 서비스가 그대로 가진다(서비스가 사용자 세션 프로세스를 종료 가능), (3) THREAT_MODEL RT-05 위험도를 올리고 구매자 안내를 강화, (4) 데이터 민감도가 높은 구매자 작업은 신뢰 노드 전용 옵션. 별도 ADR(S22).

### K2. 게임 안티치트·백신과 어떻게 부딪히는가
- **왜 중요한가**: 안티치트가 우리 프로세스를 문제 삼으면 손님의 게임 실행이 막히거나 손님 게임 계정이 제재될 수 있다. 우리가 되돌릴 수 없는 손님 피해다(THREAT_MODEL PC-03, 상위 10의 5위).
- **현재 가정**: 키보드·마우스 훅, 다른 프로세스 메모리 읽기, DLL 주입을 하지 않고 `GetLastInputInfo` 폴링과 공개 API만 쓰면(ADR 0011) 주요 안티치트가 문제 삼지 않는다.
- **해소**: 실기(S18) — PC방 인기 게임 상위 몇 개(안티치트 종류가 다른 것으로 고른다)를 에이전트 실행 중에 켜고 실행·접속·한 판 플레이가 되는지 확인. 파일럿(S31)에서 사장님께 문제 게임 보고 경로를 둔다.
- **판정 기준**: 확인한 게임 모두 정상, 안티치트 경고 0.
- **틀리면**: (1) 문제 게임의 실행 파일이 보이면 에이전트가 GPU 작업뿐 아니라 헬퍼 폴링까지 멈추는 '게임 중 완전 정지' 모드, (2) 헬퍼를 게임 실행 중 아예 종료(입력 감지는 게임 실행 자체를 손님 신호로 대체), (3) 안티치트 업체 화이트리스트 신청(사람, 코드 서명 필요). 최악이면 해당 게임이 있는 매장은 제외.

### K3. PC방 복원 솔루션이 무엇을 되돌리는가
- **왜 중요한가**: 신원(키)·모델 캐시·설치 폴더가 재부팅마다 사라지면 매 부팅 재부착과 수 GB 재다운로드가 생긴다(ADR 0008, 0015).
- **현재 가정**: 대부분의 매장에 복원되지 않는 드라이브(예: D:)가 있거나 예외 폴더를 둘 수 있다(ARCHITECTURE 11절 7번).
- **해소**: 실기(S20) — 영구성 점검 도구로 재부팅 전후 파일·레지스트리·서비스 등록이 남는지 확인. 파일럿 매장마다 사용 중인 복원 솔루션 종류와 설정을 기록.
- **판정 기준**: 영구 폴더의 파일이 재부팅 뒤 남고, 서비스가 자동 시작된다.
- **틀리면**: (1) 이미지 모드 + 재부착으로 노드 수는 유지(이미 설계됨), (2) 모델은 LAN 캐시 노드 1대만 영구 드라이브를 쓰게 하고 나머지는 부팅마다 LAN에서 받기, (3) 캐시 노드조차 복원되면 사장님께 '영구 드라이브 지정'을 설치 조건으로 요구(설치 안내 S31), (4) 서비스 등록이 복원되면 마스터 이미지에 포함시키는 절차(S21 'image 모드').

### K4. PC방 네트워크
- **왜 중요한가**: 에이전트는 나가는 443(WSS)만 쓰지만, 매장 방화벽·DPI·프록시가 WebSocket을 끊거나 오래 열린 연결을 자를 수 있다. LAN 캐시는 PC끼리 통신이 되어야 한다(클라이언트 격리 설정이면 불가).
- **현재 가정**: 나가는 443은 열려 있고, 같은 매장 PC끼리 사설 대역 통신이 된다.
- **해소**: 실기(S20) — 프록시 설정 지원, 연결 유지 시험(1시간 이상), LAN 캐시 접근 시험. 파일럿(S31) 설치 점검표에 '네트워크 점검' 단계.
- **판정 기준**: 1시간 동안 재연결 0~1회, LAN 캐시 내려받기 성공.
- **틀리면**: (1) WebSocket이 막히면 HTTPS 롱폴링 대체 전송(프로토콜 메시지는 그대로, 전송층만 교체 — S02 스키마가 전송과 분리돼 있어 가능), (2) 유휴 끊김이면 하트비트 간격 단축(T9 → 설정, 단 T10·T11 부등식 유지), (3) LAN 통신이 막히면 캐시 없이 서버에서 받되 매장 동시 다운로드 1대로 제한.

### K5. GPU 간 출력 비결정성
- **왜 중요한가**: 중복 실행 검증은 '같은 모델·같은 시드면 GPU가 달라도 앞부분이 같다'에 기댄다(ADR 0007, ARCHITECTURE 11절 3번). 갈라지면 성실한 매장이 억울하게 의심받거나 검증이 무력해진다.
- **현재 가정**: 같은 llama.cpp 버전·같은 양자화 파일·같은 시드·같은 샘플러 설정이면 서로 다른 NVIDIA 소비자 GPU에서 앞 32토큰이 대부분(목표 90% 이상의 작업에서) 같다.
- **해소**: 자동(S13 — 시뮬레이션에서 일치율이 낮을 때도 판정이 inconclusive로 안전하게 떨어지는지), 실기(S19 — GPU 2종 이상에서 같은 프롬프트 묶음의 출력 일치율 측정).
- **판정 기준**: 앞 32토큰 완전 일치율 ≥ 90%(목표).
- **틀리면**: (1) 비교 기준을 '앞 K토큰'에서 **교사 강제(teacher-forced) 로그확률 검사**로 바꾼다 — 검증 노드가 원 노드의 출력을 입력으로 받아 각 토큰의 로그확률을 계산하고, 그 모델이 그 출력을 낼 법했는지를 본다(GPU 차이에 강하다), (2) 그 전까지 카나리아(신뢰 노드 정답) 비중을 올리고 중복 실행은 평판 '보조 신호'로만, (3) 그리디(temperature 0) 작업 비교를 우선.

### K6. GPU·모델별 처리량(tokens/s)
- **왜 중요한가**: 매장 수익 추정(BUSINESS_CONTEXT 7절)과 가격, 작업 시간 추정, 진행 없음 제한(T35), 처리량 이상치 탐지(THREAT_MODEL AGT-03)의 기준이다.
- **현재 가정**: 숫자를 지어내지 않는다. S07은 공개 벤치마크(출처 표기) 또는 넓은 범위로 둔다.
- **해소**: 실기(S19 bench 도구) — RTX 4060·4070 등 GPU × 후보 모델 × 양자화별 처리량·VRAM·전력. 결과를 S07 `assumptions.json`에 반영.
- **틀리면(예상보다 느리면)**: (1) 더 작은 모델·더 강한 양자화로 후보 변경(S09), (2) 대화형보다 배치 위주로 영업, (3) 사장님 수익 추정을 즉시 고치고 파일럿 안내 문구 갱신(S31 주장-근거표).

### K7. 손님 없는 시간 분포
- **왜 중요한가**: 수익의 가장 큰 변수다. 빈 시간이 10~30분 조각이면 `minIdleMinutes`(10분)와 모델 로딩을 빼고 남는 시간이 거의 없다(ARCHITECTURE 11절 1번).
- **현재 가정**: 하루 약 8시간, 새벽·평일 오전에 길게 이어진다(BUSINESS_CONTEXT 7절 — 가정).
- **해소**: 파일럿(S31) — `presence_intervals`에서 PC별 빈 구간 길이 분포를 2주 이상 수집, `tools/pilot-report`가 요약. S07 시뮬레이터에 넣는다.
- **틀리면**: (1) 배치 우선·짧은 작업 단위, (2) 안정성 예측(S12)으로 오래 빌 PC에 긴 작업, (3) 모델을 메모리에 미리 올려 두는 '예열'은 손님 영향(VRAM 점유) 때문에 하지 않는다 — 대신 작은 모델로 로딩 시간 단축, (4) `minIdleMinutes`를 줄이는 것은 손님 보호 약화라 사장님 동의와 데이터 근거가 있을 때만(ADR 0016).

### K8. nvidia-smi 전력값 정확도
- **왜 중요한가**: 사장님 화면의 전기요금 추정이 이 값에 기댄다. 틀리면 '숫자는 정직하게'(BUSINESS_CONTEXT 13절 3번)가 깨진다.
- **현재 가정**: nvidia-smi `power.draw`는 GPU 보드 전력만 잰다. PC 전체(CPU·메모리·팬·전원 손실)는 빠진다. 따라서 그대로 쓰면 과소 추정이다.
- **해소**: 실기(S19) — 벽 전력계(사람이 준비)로 같은 작업 중 PC 전체 전력을 재고 nvidia-smi 값과 비율을 구한다.
- **틀리면(차이가 크면)**: 사장님 화면은 'GPU 측정값 × 보정 계수(실측)'로 보여 주고 '추정'으로 표시한다. 보정 계수가 없으면 GPU 값과 함께 '실제 전기 사용은 더 많을 수 있음'을 명시.

### K9. 백신 오탐(Go 바이너리)
- **왜 중요한가**: Go로 만든 서명 없는 바이너리는 백신이 의심하는 경우가 잦다. 설치가 막히거나 실행 중 격리되면 노드가 사라진다. PC방은 백신·보안 프로그램을 여러 개 쓰기도 한다.
- **현재 가정**: 코드 서명 인증서(사람이 준비, HUMAN_TODO)로 서명하면 대부분 해결된다.
- **해소**: 실기(S21) — Windows Defender와 PC방에서 흔한 백신으로 설치·실행 확인, 필요하면 백신 업체 오탐 신고. CI 산출물을 온라인 다중 백신 검사에 올리는 것은 바이너리 공개가 되므로 사람이 판단.
- **틀리면**: (1) 코드 서명(EV 인증서면 평판 축적이 빠름), (2) 업체별 오탐 신고 절차를 런북에, (3) 설치 안내에 예외 등록 방법(사장님용).

### K10. VRAM 해제 시간과 잔존값
- **왜 중요한가**: 선점 SLO-2(입력 → VRAM 해제 p95 2초)와 데이터 잔존(THREAT_MODEL PC-07)이 드라이버 동작에 달려 있다.
- **현재 가정**: 프로세스 종료 뒤 드라이버가 2초 안에 VRAM을 돌려주고, 새 할당은 이전 내용을 노출하지 않는다.
- **해소**: 실기(S18·S19 — 종료 → nvidia-smi 메모리 0까지 시간 반복 측정), 실기(S22 — 큰 버퍼를 할당해 이전 런타임의 표식 문자열이 보이는지 확인).
- **틀리면**: (1) 해제가 느리면 선점 판단을 앞당긴다(입력 감지 전 '손님 접근' 신호 — 예: 로그인 화면 활성 — 를 쓸 수 있는지 S18이 검토), 모델을 작게, (2) 잔존값이 보이면 정상 종료 경로(완료·취소)에서는 런타임이 버퍼를 지운 뒤 종료하고, 선점 경로는 수용한 위험으로 남겨 구매자 안내에 적는다.

### K11. 입력 감지가 놓치는 손님 활동
- **왜 중요한가**: `GetLastInputInfo`는 키보드·마우스 입력을 본다. 게임패드(XInput) 입력, 영상만 보는 손님, 원격 데스크톱 세션은 잡히지 않을 수 있다(ARCHITECTURE 11절 2번).
- **현재 가정**: 게임패드로 게임하면 전체 화면·GPU 3D 사용 신호가 함께 잡는다. 영상 시청은 오디오 재생·비디오 디코드 신호(D8)로 잡는다.
- **해소**: 실기(S18) — 게임패드만으로 플레이, 창 모드 영상 재생, 음악만 재생, 원격 접속 각각에서 적격 판정이 '작업 불가'가 되는지 확인.
- **틀리면**: (1) XInput 상태 폴링을 헬퍼에 추가(훅이 아니라 공개 API 폴링), (2) 오디오·디코드 신호를 못 읽는 환경이면 그 신호를 '불확실 = 멈춤'으로 처리, (3) PC방 관리 프로그램의 '손님 로그인' 신호 연동을 앞당긴다.

### K12. 모델 로딩·런타임 종료 시간
- **왜 중요한가**: 첫 토큰 지연(대화형 체감), 진행 없음 제한 T35(첫 청크 60초), 선점 T5(종료 0.5초)가 이 값에 달려 있다.
- **현재 가정**: 8~12GB GPU용 중소형 모델 로딩은 수십 초 이내, `TerminateJobObject` 뒤 프로세스 종료 확인은 0.35초 이내.
- **해소**: 실기(S19 bench) — 냉시작·디스크 캐시 있음 각각 로딩 시간, 종료 시간 분포.
- **틀리면**: (1) 로딩이 길면 대화형은 이미 모델이 올라간 노드만 받게 하는 하드 조건, T35 첫 청크 값을 로딩 시간 p95 + 여유로 조정(설정 검증 부등식 T35 < T21 유지), (2) 종료가 느리면 선점 경로에서 종료 확인을 기다리지 않고 GPU 사용 중지(프로세스 일시 중단)부터 하는 2단계 선점 검토(S18 ADR).

### K13. 매장 GPU 사양 분포
- **왜 중요한가**: 돌릴 수 있는 모델 후보(S09)와 수익이 VRAM(8GB / 12GB 등)에 달려 있다(BUSINESS_CONTEXT 10절 성능).
- **현재 가정**: RTX 4060(8GB)·4070(12GB) 계열이 주력.
- **해소**: 파일럿 섭외 때 사장님께 확인(사람), 등록된 노드의 `status` GPU 보고(자동, S10).
- **틀리면**: 8GB 미만이 많으면 더 작은 모델 위주, 구형 GPU는 배치 전용 또는 제외.

### K14. 사장님이 밤에 PC를 끄는가, 관리 프로그램이 PC를 잠그는가
- **왜 중요한가**: 손님 없는 시간에 PC가 꺼져 있거나, PC방 관리(요금) 프로그램이 로그아웃 상태에서 화면을 잠그고 프로세스를 정리하면 가용 시간 자체가 사라진다.
- **현재 가정**: 손님 없는 시간에도 PC는 켜져 있다(BUSINESS_CONTEXT 7절 '손님 없는 시간이 확실하다'). 관리 프로그램은 우리 서비스를 죽이지 않는다.
- **해소**: 파일럿 섭외 설문(사람, S31), 실기(S20 — 관리 프로그램 잠금 화면 상태에서 서비스·헬퍼 동작 확인).
- **틀리면**: (1) Wake-on-LAN으로 정해진 시간대에 켜는 기능(사장님 동의, 매장 정책), (2) 잠금 화면 상태를 '손님 없음'으로 판정할 수 있는지 S18에서 검토(헬퍼가 없는 세션이면 서비스 자체 신호로), (3) 관리 프로그램 업체와 예외 등록 협의(사람).

### K15. WebSocket 연결당 메모리·관리형 Postgres 제약
- **왜 중요한가**: 규모 단계 전환 시점(ARCHITECTURE 8절, 연결당 약 64 KB는 '확인 필요')과 운영 비용이 이 값에 달려 있다. 관리형 Postgres 저가 티어는 직접 연결 수와 `LISTEN` 지원(풀러 경유 불가)에 제약이 있을 수 있다.
- **현재 가정**: 단일 프로세스가 노드 1,000대까지 버틴다. `LISTEN`은 전용 직접 연결 1개로 충분하다.
- **해소**: 자동(S11 부하 시험, S27 두 인스턴스 시나리오), 배포 시 확인(S30 — 선택한 관리형 DB의 연결 제한·`LISTEN` 지원을 날짜와 함께 기록).
- **틀리면**: 단계 B(게이트웨이 분리) 시점을 앞당기거나, `LISTEN/NOTIFY` 대신 짧은 주기 폴링으로 대체(지연 증가 — 킬스위치는 T17 재조정 루프가 1차 안전망이 되므로 T16 목표를 다시 잰다).

### K16. 외부 제공사 약관과 선불 크레딧 법적 성격
- **왜 중요한가**: 외부 모델 재판매가 제공사 약관상 허용되는지, 제공사가 요청 데이터를 얼마나 보관하는지, 선불 크레딧이 전자금융거래법상 무엇인지가 2단계(크레딧 판매·환전) 진입 조건이다(BUSINESS_CONTEXT 10·12절).
- **현재 가정**: 확인 전. 그래서 실결제·출금은 코드가 없고(MVP 3절), 외부 실제 호출은 세 겹 스위치로 잠겨 있다.
- **해소**: 사람(법률 검토 — HUMAN_TODO '나중에' 항목).
- **틀리면**: 재판매 불가면 외부 모델 환전은 구매자 자신의 키를 쓰는 '대리 호출' 형태로 바꾸거나 제외. 선불 크레딧이 규제 대상이면 발행 한도·보증 등 요구 사항에 맞춰 원장 계정·준비금 규칙을 새 ADR로 조정(원장 구조는 통화·계정 추가로 대응 가능).

### K17. AMD(Vulkan) 시험 노드에서 무엇이 동작하는가
- **왜 중요한가**: 지금 가진 실기 PC는 AMD RX 5700 XT(8GB, RDNA1) 한 대다(ADR 0019). 이 PC로 할 수 있는 실기 확인의 범위가 아래 세 가지에 달려 있다.
- **현재 가정**: (1) Windows 성능 카운터 `GPU Process Memory`(Dedicated Usage)가 프로세스별 VRAM을 보여 주고, 프로세스 종료 뒤 0이 된다. (2) llama.cpp Vulkan 빌드가 세션 0 서비스에서도 GPU를 쓴다. (3) Ollama가 이 GPU를 가속하지 못하면 CPU로 돌아가고, 데모 흐름은 그대로 된다.
- **해소**: 실기(S04 데모 — Ollama가 GPU를 쓰는지 `ollama ps`로 확인, S18·S19 — 종료 → 카운터 0까지 시간 반복 측정, S22 — 서비스 계정으로 Vulkan `llama-server` 실행).
- **틀리면**: (1) 카운터를 믿을 수 없으면 AMD 노드의 VRAM 해제 확인을 '프로세스 트리 종료 + 어댑터 전체 사용량 감소'로 대체한다(ADR 0019 재검토 조건). (2) 세션 0에서 Vulkan이 안 되면 K1의 대안(사용자 세션 저권한 계정 실행)을 AMD에 먼저 적용해 시험한다. (3) Ollama가 CPU로만 돌면 데모는 작은 모델로 하고, GPU 경로는 S19 Vulkan `llama-server`로 확인한다.
