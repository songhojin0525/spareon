# 0017. 프로토콜 JSON은 '엄격 JSON + 정수만'으로 제한하고, 서명은 정규화 바이트에, 타입은 자체 생성기로 만든다

- 상태: 채택
- 날짜: 2026-10-09
- 차수: S02

## 맥락
- ADR 0003으로 에이전트(Go)와 서버(TS)가 같은 JSON Schema로 검증하기로 했다. 그런데 스키마가 같아도 **JSON을 읽는 단계**가 언어마다 다르다.
  - JS `JSON.parse`는 모든 숫자를 64비트 실수로 읽는다. `5.0000000000000001`은 정수 5가 되고, 2^53을 넘는 정수는 반올림된다. Go 검증기는 정확한 값(`big.Rat`)으로 본다 → 같은 메시지에 대해 한쪽은 통과, 한쪽은 거부.
  - 중복 키, 짝 없는 UTF-16 서로게이트 이스케이프(`\ud800`), BOM, 잘못된 UTF-8, 아주 깊은 중첩을 언어마다 다르게 처리한다(Go는 서로게이트를 U+FFFD로 바꾸고, 깊이 10000에서 멈춘다).
  - 정규식: Go(RE2)는 반복 횟수 곱이 1000을 넘는 패턴을 거부하고, JS는 받아들인다(S02에서 실제로 걸렸다).
- 서명(인증·등록·매니페스트)은 바이트가 하나라도 다르면 실패하거나, 더 나쁘게는 '서명한 내용'과 '해석한 내용'이 달라질 수 있다(THREAT_MODEL AGT-14·AGT-16, S02 적대적 검토 포인트).
- PC 수천 대가 같은 프로토콜을 쓰므로 한쪽만 다르게 해석하면 한꺼번에 고장 난다.

## 결정
1. **엄격 JSON**: 파싱 전에 직접 짠 인식기로 다음을 거부한다(TS·Go 같은 알고리즘, 공유 벡터 55개로 고정): 잘못된 UTF-8, BOM, 공백 외 문자, 깊이 > 32, 같은 객체 안 중복 키(이스케이프를 푼 뒤 비교), 짝 없는 서로게이트 이스케이프, 소수점·지수가 있는 숫자, 16자리 넘는 정수. 통과한 입력은 두 언어의 표준 파서가 같은 값으로 읽는다.
2. **정수만**: 프로토콜 숫자는 모두 정수이고, 스키마에 `minimum`·`maximum`(|값| ≤ 2^53−1)이 있다. 실수가 필요한 값은 단위를 바꾼다(`temperatureMilli` 0~2000, `topPMilli` 1~1000). 해시·키·nonce·서명은 소문자 hex 문자열이다(base64는 같은 바이트의 다른 표기가 있어 쓰지 않는다). 돈은 프로토콜에 없다.
3. **정규화 JSON**(RFC 8785 부분집합: 키는 UTF-16 순, 공백 없음, 최소 이스케이프, 정수만)으로 스키마 번들 해시(`protocolHash`)와 매니페스트 서명 대상을 만든다.
4. **서명 대상 바이트**는 `도메인 문자열 + "\n" + 구성요소들("\n"로 연결)`이다. 구성요소는 줄바꿈이 들어갈 수 없는 형식(소문자 hex, UUIDv7)으로 먼저 검사하고 아니면 바이트를 만들지 않는다. 서명 검증은 형식이 정확한 hex만 받고, S ≥ L(비정규 스칼라)은 두 언어 모두 명시적으로 거부한다.
5. **매니페스트는 검증 후 파싱**: 메시지에 매니페스트를 정규화 JSON **문자열 그대로** 싣고, 받은 바이트 그대로 서명을 확인한 뒤, 엄격 파싱 → 다시 정규화한 결과가 받은 문자열과 같은지 → 스키마 순으로 확인한다.
6. **자체 코드 생성기**(`packages/protocol/scripts/gen.ts`): 스키마에서 TS 타입, Go 구조체, 정규화 번들(양쪽 내장), 해시·한도·레지스트리 상수를 만든다. 생성기는 허용한 스키마 부분집합만 받고 규칙 위반(최대 길이 없는 문자열, maxItems 없는 배열, 범위 없는 정수, `format`, 사람이 읽는 문구, 앵커 없는 패턴, 열린 객체)이 있으면 실패한다. 생성물이 낡으면 테스트가 실패한다.

## 검토한 대안
| 대안 | 장점 | 단점 | 버린 이유 |
|---|---|---|---|
| 표준 파서만 쓰고 fixture로 차이 확인 | 코드 적음 | fixture가 모든 차이를 덮지 못한다. 차이가 생겨도 운영에서야 드러난다 | 계약을 구조로 보장하지 못함 |
| 64비트 정수를 문자열로 | 범위 제한 없음 | 모든 숫자 필드가 문자열이 되어 검증·사용이 번거롭다 | 프로토콜에 2^53을 넘는 값이 없다(바이트 크기도 2^50 미만) |
| 실수 허용 + 소수 자릿수 제한 | API와 같은 표기 | 여전히 JS 반올림과 Go 정밀 비교의 경계 사례가 남는다 | 정수 단위 변환이 더 단순하고 확실 |
| 매니페스트를 객체로 싣고 양쪽이 각자 정규화 | 메시지가 읽기 쉽다 | 파서 차이가 '서명한 것과 읽은 것이 다른' 우회가 될 수 있다 | 서명은 전송된 바이트에 대해 확인해야 한다 |
| `json-schema-to-typescript` + Go용 별도 생성기 | 검증된 도구 | 두 도구의 해석 차이, 선택 필드·합집합 규칙을 통제 못 함, 크기 제한 강제 불가 | 단일 생성기로 규칙까지 강제 |
| Protobuf/CBOR로 전환 | 바이트 정규성 | ADR 0003의 결정(사람이 읽는 JSON, 엄격 검증)과 충돌 | 재검토 조건에 남김 |

## 결과와 트레이드오프
- 쉬워지는 것: TS와 Go가 같은 메시지에 같은 판정을 내린다는 것을 290개 fixture와 벡터로 매번 확인한다. 서명 우회(필드 경계 모호성, 다른 용도 서명 재사용, 비정규 표기, 작은 차수·비정규 공개키)가 막힌다(공개키 검사는 S02 게이트 검토에서 추가, 섞인 차수 키의 부분군 검사는 하지 않음). 크기 제한 누락이 생성 단계에서 막힌다.
- 어려워지는 것: 실수 값이 필요한 새 필드는 단위를 정해야 한다. 생성기를 우리가 유지한다(스키마 부분집합이 작아 400줄 안팎). 엄격 인식기를 두 언어로 똑같이 유지해야 한다(공유 벡터가 지킨다).
- 서버 쪽 메시지 처리 비용이 조금 늘어난다(파싱 전 한 번 더 훑는다). S11 부하 측정에서 확인한다.

## 재검토 조건
- S11 부하 측정에서 엄격 인식기 + Ajv 검증이 메시지 처리 CPU의 절반을 넘을 때.
- 실수 값이 꼭 필요한 필드가 여러 개 생길 때(이진 형식이나 십진 문자열 규칙 검토).
- 스키마에 생성기가 지원하지 않는 기능(판별 합집합 등)이 꼭 필요해질 때.
