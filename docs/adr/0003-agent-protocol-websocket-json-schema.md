# 0003. 에이전트 프로토콜은 WebSocket 위의 JSON 메시지이고, JSON Schema가 단일 진실 원천이다

- 상태: 채택
- 날짜: 2026-10-08
- 차수: S01

## 맥락
- 에이전트(Go)와 서버(TypeScript)는 언어가 다르다. 메시지 형식이 한쪽에서만 바뀌면 PC 수천 대가 한꺼번에 고장 난다(S02 목표).
- PC방 네트워크는 나가는 443만 확실히 열려 있다고 가정한다(KNOWN_UNKNOWNS: PC방 네트워크). 들어오는 연결은 못 받는다.
- 서버가 먼저 보내야 하는 명령이 있다: 작업 제안, 취소, 일시정지, 킬스위치(연결된 노드까지 1초 이내 목표, [시간 예산](../ARCHITECTURE.md#7-시간-예산)).
- 손님 PC에서 도는 프로그램이므로 메시지를 엄격하게 검증해야 한다(크기, 길이, 추가 필드).

## 결정
- 전송: TLS 위 WebSocket 하나(에이전트가 연결을 연다). 서버 쪽 `@fastify/websocket`, 에이전트 쪽 `github.com/coder/websocket`.
- 형식: 봉투 `{v, type, id, ts, corr?, payload}`. 봉투와 payload는 기본 `additionalProperties: false`, 모든 문자열·배열에 최대 길이, 메시지 최대 1 MiB, 인라인 작업 입력 256 KiB(넘으면 `inputRef`).
- 원천: `packages/protocol/schemas/`의 JSON Schema 2020-12. TS 타입·Ajv 검증기와 Go 타입·검증기를 같은 스키마에서 만든다. `protocolHash` = 정규화한 스키마 번들의 SHA-256. 서버는 지원하는 해시 집합을 갖고 모르는 해시는 `auth.fail(protocol_unsupported)`로 거부한다.
- 같은 fixture 폴더를 TS·Go가 모두 읽어 같은 판정을 내리는지 계약 테스트로 강제한다(S02).
- 등록(`enroll.*`)과 큰 입력·아티팩트 다운로드는 HTTPS다(WS 연결 전에 일어나거나 크기가 크다).
- 보완(이 ADR이 S02 명세에 더하는 것): `job.offer`에는 '검증용 작업' 표시를 넣지 않는다. 검증 작업과 일반 작업은 메시지 형태로 구별할 수 없어야 한다(ADR 0007, S13 수용 기준 4).

## 검토한 대안
| 대안 | 장점 | 단점 | 버린 이유 |
|---|---|---|---|
| gRPC(양방향 스트리밍) | 타입 생성, 효율 | HTTP/2 + 프록시 호환성 문제(PC방 프록시·방화벽), Windows에서 디버깅 어려움, 브라우저형 도구 없음 | 네트워크 미지수가 큰 환경에서 위험 |
| HTTP 롱폴링 | 프록시 친화적 | 킬스위치 1초 목표에 불리, 연결당 요청 수 많음 | 서버 푸시 지연 |
| MQTT | IoT용, 가벼움 | 브로커 운영, 인증 모델이 우리와 다름 | 운영 대상 증가 |
| Protobuf 스키마 | 작고 빠름 | 사람이 읽기 어려움, 추가 필드 거부 같은 엄격 검증이 약함 | 우리 메시지량(노드당 초당 몇 건)에서는 크기 이득이 작다 |
| TS 타입이 원천, Go는 손으로 맞춤 | 빠른 시작 | 어긋남을 테스트로 못 잡는다 | S02 목표 위반 |

## 결과와 트레이드오프
- 쉬워지는 것: 사람이 읽을 수 있는 메시지, 양쪽 같은 검증, 해시로 버전 불일치를 즉시 알아챔.
- 어려워지는 것: JSON 파싱·검증 CPU 비용(3만 노드 × 하트비트 5초 = 초당 6천 메시지. Ajv 컴파일 검증기로 감당 가능하다고 보지만 S11 부하 측정으로 확인).
- 스키마를 바꾸면 해시가 바뀌므로 깨지지 않는 변경도 서버가 옛 해시를 같이 지원해야 한다(지원 해시 집합 + 업데이트 단계적 배포, ADR 0015).

## 재검토 조건
- S11 부하 측정에서 메시지 처리 CPU가 인스턴스 하나의 50%를 넘을 때(바이너리 형식 검토).
- PC방 네트워크 실측(S20, 파일럿)에서 WebSocket이 막히는 매장이 나올 때(HTTPS 롱폴링 대체 경로 검토).
