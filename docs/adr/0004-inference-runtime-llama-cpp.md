# 0004. 추론 런타임은 버전을 고정한 llama.cpp `llama-server`, 개발용으로 Ollama 어댑터를 둔다

- 상태: 채택
- 날짜: 2026-10-08
- 차수: S01

## 맥락
- PC방 GPU는 게임용(RTX 4060 8GB, 4070 12GB 등, BUSINESS_CONTEXT 10절). 한 PC에 통째로 들어가는 양자화된 중소형 모델만 돌린다(4절 3번).
- 손님이 오면 0.5초 안에 프로세스를 죽이고 VRAM을 비워야 한다(ADR 0016). 런타임은 '언제 죽여도 되는' 별도 프로세스여야 한다.
- 노드는 서명이 확인된 파일만 실행한다(S09). 외부(GitHub 등)에서 직접 받지 않는다.
- 검증(ADR 0007)에는 temperature 0·시드 고정 같은 결정적 모드와 이어쓰기(접두사 완성)가 필요하다.
- 개발자·친구 PC 데모(0단계)는 설치가 쉬워야 한다.

## 결정
- 운영 런타임: llama.cpp `llama-server`의 특정 빌드(Windows CUDA 빌드)를 우리가 받아 SHA-256과 ed25519 서명을 붙여 아티팩트 저장소에 올린다. 에이전트는 이것만 내려받아 검증 후 실행한다(S09, S19).
- 실행 원칙: 127.0.0.1 무작위 포트, 무작위 API 키, 프롬프트 로그·디스크 캐시·슬롯 저장 끔, 동시 슬롯 1, Windows Job Object 안에서 실행(종료 시 트리 전체 종료). 플래그 이름은 고정한 버전의 `--help`로 확인해 S19 문서에 적는다.
- 모델 형식: GGUF. 모델 파일도 서명 매니페스트로 배포한다.
- 개발용: Ollama 어댑터(`http://127.0.0.1:11434`)는 같은 `Runtime` 인터페이스로 둔다. 운영 설정(서비스 모드)에서는 Ollama를 거부한다.
- 테스트용: 결정적 가짜 런타임(Go)과 가짜 `llama-server`(HTTP 흉내).

## 검토한 대안
| 대안 | 장점 | 단점 | 버린 이유 |
|---|---|---|---|
| vLLM | 높은 처리량, 배치 | Windows 공식 지원 약함, VRAM 사전 점유, 무거운 Python 배포 | Windows 게임 PC에 부적합 |
| Ollama를 운영에도 | 설치 쉬움, 모델 관리 | 자체 업데이트·모델 저장소를 가져 우리 서명 체계와 겹침, 백그라운드 서비스가 상주, 버전 고정·플래그 통제가 어렵다 | 신뢰 경계를 우리가 통제할 수 없다 |
| ONNX Runtime / TensorRT-LLM | 성능 | 모델별 변환·빌드 부담, GPU 세대별 엔진 | 1인 운영에 과함 |
| llama.cpp를 라이브러리로 링크(cgo) | 프로세스 하나 | 에이전트가 런타임과 같이 죽고 같이 크래시, 강제 종료로 VRAM을 확실히 비우기 어렵다 | 선점 보장이 약해진다 |

## 결과와 트레이드오프
- 쉬워지는 것: 프로세스 종료 = VRAM 해제로 선점 경로가 단순하다. 버전이 고정되어 GPU 간 출력 비교(검증)가 덜 흔들린다.
- 어려워지는 것: llama.cpp는 매우 빨리 바뀐다. 업그레이드는 서명·단계적 배포(ADR 0015)와 검증 기준 재측정(GPU 간 비결정성)을 다시 거쳐야 한다.
- 처리량은 vLLM보다 낮다. 이 사업의 수요(느려도 되는 대량 작업)에서는 받아들인다.
- AMD·인텔 GPU는 v0.1에서 지원하지 않는다(MVP 비목표).

## 재검토 조건
- 실측(S19 bench)에서 같은 GPU의 처리량이 대안 런타임 대비 50% 미만으로 나올 때.
- 파일럿 매장에 NVIDIA가 아닌 GPU 비율이 20%를 넘을 때(Vulkan 빌드 검토).
- llama.cpp 라이선스(MIT)나 배포 정책이 바뀔 때.
