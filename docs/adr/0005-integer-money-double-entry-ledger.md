# 0005. 돈은 정수 최소 단위로만 다루고, 모든 잔액 변화는 통화별 합이 0인 이중기입 원장 거래로만 일어난다

- 상태: 채택
- 날짜: 2026-10-08
- 차수: S01

## 맥락
- 크레딧은 장차 화폐가 되려는 것이다(BUSINESS_CONTEXT 1·5절). 장부가 한 번이라도 틀리면 신뢰는 끝난다(S06).
- 여러 통화가 섞인다: 크레딧(CR), 원화(준비금, KRW), 달러(외부 제공사 원가, USD).
- 동시에 수천 건의 홀드·캡처, 재시도, 서버 재시작이 일어난다.
- 무료 테스트 충전으로 만든 크레딧이 매장 수익을 거쳐 실제 현금 정산으로 빠져나가는 경로가 있다([ARCHITECTURE 이견 절](../ARCHITECTURE.md#12-이견-명세와-다르게-설계한-것)).

## 결정
- 단위: µCR(1 CR = 1,000,000 µCR), µUSD, 원(KRW 최소 단위). 코드에서는 브랜드 bigint 타입(`MicroCredits`, `MicroUsd`, `Won`)만 쓴다. 부동소수점은 돈 경로에서 린트로 금지(S00 규칙).
- 원장: 거래(`ledger_tx`) 하나에 여러 기입(`ledger_postings`). **통화별 기입 합 = 0**을 DB 제약(지연 제약 트리거)과 앱 양쪽에서 강제한다. 잔액 행은 기입과 같은 트랜잭션에서만 바뀐다. 잔액을 바꾸는 코드는 `ledger` 모듈 하나뿐이다.
- 통화 간 이동은 통화별 '변환 계정'을 거쳐 통화마다 따로 합 0을 맞춘다. 환율은 거래에 스냅숏 ID로 남긴다.
- 통화 목록: `CR`(실제 자금이 뒷받침하는 크레딧), `TCR`(샌드박스 크레딧 — 구매자 셀프 테스트 충전용, 정산·실제 외부 호출 불가), `KRW`, `USD`. TCR로 결제된 작업의 매장 수익은 TCR로 쌓이고 `MANUAL_PAYOUT_RECORD`의 대상이 아니다. 운영자만 할 수 있는 `TEST_TOPUP`(파일럿에서 창업자가 실제로 낸 돈을 기록)은 CR이다.
- 모든 원장 함수는 멱등 키를 받는다(같은 키 재호출 = 같은 결과, 두 번 기록 없음). 작업 관련 키는 `<jobId>:<단계>`.
- 반올림: 한 거래 안에서 한 번만, 방향을 명시한다. 작업 비용은 올림(구매자에게 표시), 노드 몫은 내림, 플랫폼 몫 = 비용 − 노드 몫(합이 정확히 비용). 원화 → 크레딧은 내림(구매자에게 불리하지 않게 차액 표시). 세부는 S08 `PRICING.md`.
- 캡처는 홀드를 넘지 않는다: `capture = min(계산한 비용, 홀드)`. 넘는 부분은 플랫폼이 부담하고 지표로 남긴다(서버 토큰 재계산이 견적보다 커지는 드문 경우).
- 잠금 순서: 잔액 행을 계정 ID 순으로 `FOR UPDATE`. 직렬화 실패·교착은 제한 횟수 지수 백오프 재시도.
- 대사: 잔액 = 기입 합, 거래별 통화 합 0, 홀드 계정 = 활성 홀드 합, 미성숙 수익 계정 = 미성숙 수익 합. 하나라도 어긋나면 `ledger_frozen` 플래그로 외부 환전·성숙 처리·정산 기록을 자동 정지한다(fail-safe).

## 검토한 대안
| 대안 | 장점 | 단점 | 버린 이유 |
|---|---|---|---|
| 사용자 테이블의 `balance` 열만 갱신 | 단순 | 이력·대사 불가, 경합 시 조용히 틀림 | 돈이 사라져도 모른다 |
| `numeric`/소수 크레딧 | 사람이 읽기 쉬움 | 앱에서 부동소수점으로 새기 쉽다 | 절대 규칙 3 |
| 이벤트 소싱(잔액은 매번 재계산) | 감사 완벽 | 조회가 느림, 1인 운영에 복잡 | 잔액 캐시 + 대사로 같은 신뢰를 더 싸게 얻는다 |
| 테스트 크레딧을 같은 CR로 두고 플래그로 구분 | 통화 하나 | 홀드·캡처·수익마다 출처를 추적해야 하고 섞이면 구분 불가 | 통화를 나누면 합 0 제약이 저절로 분리해 준다 |
| 외부 원장 서비스(예: 관리형 원장 API) | 검증된 구현 | 비용, 외부 의존, 오프라인 테스트 불가 | 저비용·Docker 없는 테스트 원칙 |

## 결과와 트레이드오프
- 쉬워지는 것: "돈이 생기거나 사라지지 않는다"를 DB 제약 + 속성 테스트로 증명할 수 있다. 사장님 화면 숫자는 원장에서만 나온다.
- 어려워지는 것: 모든 기능이 원장 API를 거쳐야 한다(직접 UPDATE 금지). 플랫폼 매출 계정처럼 모든 캡처가 건드리는 계정은 잠금 경합 지점이 된다 → 규모 단계에서 계정을 여러 개로 나눈다([ARCHITECTURE 규모 절](../ARCHITECTURE.md#8-규모-가정과-확장-경로)).
- TCR 때문에 화면·가격표가 통화를 의식해야 한다(같은 가격표를 쓰되 통화 표시).

## 재검토 조건
- 실제 결제(로드맵 2단계)를 켤 때: 결제 대행사 정산·환불·차지백 흐름을 원장 거래 종류로 추가하는 ADR.
- 토큰 발행이 합법화되어(로드맵 3~4단계) 크레딧이 외부 체인에 기록될 때.
- 원장 처리량이 S06 목표(초당 캡처 200건)에 못 미치고 계정 분할로도 해결되지 않을 때.
