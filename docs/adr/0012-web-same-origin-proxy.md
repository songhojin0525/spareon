# 0012. 웹은 `/api/*`를 Next.js rewrite로 서버에 프록시해 같은 출처 쿠키 세션을 쓴다

- 상태: 채택
- 날짜: 2026-10-08
- 차수: S01

## 맥락
- 사장님·구매자·운영자 화면은 사람 로그인(세션 쿠키, S05)을 쓴다. 쿠키는 httpOnly·Secure·SameSite=Lax.
- 웹(Next.js)과 서버(Fastify)는 따로 배포된다(웹 호스팅 + VPS, S30). 출처가 다르면 CORS·서드파티 쿠키 차단·CSRF 설정이 복잡해진다.
- 구매자 API(`/v1/*`)는 사람 세션이 아니라 API 키(Bearer)로 쓰고, OpenAI SDK가 서버를 직접 부른다.

## 결정
- 브라우저는 웹 출처 하나만 본다. 웹의 `/api/*`는 Next.js rewrite로 서버(`SERVER_URL`)에 그대로 전달된다. 세션 쿠키는 웹 출처의 1st-party 쿠키가 된다.
- 서버는 상태를 바꾸는 요청에 Origin/Referer = `WEB_ORIGIN` 확인 + 이중 제출 CSRF 토큰을 요구한다(S05).
- 서버는 프록시를 거친 요청의 클라이언트 IP를 신뢰할 프록시 목록 기준으로만 해석한다(속도 제한·감사 IP 해시용). 목록 밖의 `X-Forwarded-For`는 무시한다.
- 구매자 API(`/v1/*`)와 에이전트 WS·아티팩트 다운로드는 서버 도메인으로 직접 간다(프록시 안 거침). 쿠키 인증을 받지 않는다.
- CORS: 서버는 기본적으로 브라우저 교차 출처 요청을 허용하지 않는다(`/v1/*`는 API 키 전용이므로 필요하면 나중에 명시적으로 연다).

## 검토한 대안
| 대안 | 장점 | 단점 | 버린 이유 |
|---|---|---|---|
| 웹이 서버를 교차 출처로 직접 호출(CORS + 쿠키) | 프록시 홉 없음 | 서드파티 쿠키 정책, `SameSite=None` 필요 → CSRF 위험 증가 | 보안·호환성 |
| 웹 서버 쪽 BFF가 토큰을 들고 서버 호출 | 브라우저에 토큰 없음 | 세션 저장소가 둘, 구현량 증가 | 1인 운영 |
| 서버와 웹을 한 도메인 하위 경로로 리버스 프록시(Caddy) | 홉 하나 | 웹 호스팅(Vercel)을 쓰면 불가, 배포 결합 | 배포 유연성 |
| 브라우저에 JWT 저장 | 무상태 | XSS 시 토큰 탈취, 폐기 어려움 | 세션 쿠키가 더 안전 |

## 결과와 트레이드오프
- 쉬워지는 것: 쿠키·CSRF 모델이 단순하다. 웹과 서버를 따로 배포해도 같은 출처.
- 어려워지는 것: 웹 호스팅 → 서버 홉이 하나 늘어 지연이 생긴다(사람 화면이라 허용). 스트리밍 응답(플레이그라운드, S25)이 rewrite를 통과하는지 S23·S25에서 확인해야 한다. 웹 호스팅 요청 시간 제한이 긴 요청을 끊을 수 있다(플레이그라운드는 짧게).
- 프록시 뒤라 실제 클라이언트 IP 처리에 주의(위 결정).

## 재검토 조건
- 웹 호스팅의 rewrite가 SSE 스트리밍을 버퍼링하거나 끊는 것이 확인될 때(플레이그라운드만 서버 직접 호출 + API 키로 전환 검토).
- 웹과 서버를 같은 VPS에서 Caddy로 함께 서비스하기로 바꿀 때.
