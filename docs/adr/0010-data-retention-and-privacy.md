# 0010. 구매자 데이터는 최소로, 짧게, 암호화해서 보관한다 — 노드에서는 메모리에만

- 상태: 채택
- 날짜: 2026-10-08
- 차수: S01

## 맥락
- 구매자 프롬프트·출력이 남의 매장, 손님이 앉는 PC에서 처리된다(BUSINESS_CONTEXT 10절 보안 리스크). 기업은 데이터가 남의 컴퓨터로 가는 것을 꺼린다(4절 3번).
- 절대 규칙 4: 프롬프트·출력은 로그·메트릭·에러 리포트에 남기지 않는다. 노드에서는 메모리에만, 서버 보관은 암호화 + 보존 기한.
- 반대로 서버는 일부 데이터를 잠깐 가져야 한다: 재배정·이어쓰기(입력과 지금까지 출력), 배치(입력 파일, 결과 파일), 검증(중복 실행 결과 비교).

## 결정
- **분류**: 구매자 콘텐츠(프롬프트, 출력, 배치 파일) / 메타데이터(길이, 토큰 수, 해시, 시각, 모델, 비용) / 계정 데이터. 콘텐츠만 아래 규칙을 따른다. 메타데이터는 일반 보존.
- **로그·지표·에러**: 콘텐츠는 어떤 레벨에서도 남기지 않는다. pino 편집 경로(S05), 에러 객체에서 요청 본문 제거, 지표 라벨에 콘텐츠·키 금지(S29). 길이·해시만 허용. 테스트로 강제(S05·S14·S17).
- **서버 저장**: 콘텐츠는 AES-256-GCM으로 암호화해 DB에 저장한다. 키는 환경변수 `DATA_ENCRYPTION_KEY`(+ 키 ID, 교체 가능), DB와 따로 보관. 백업에는 암호문만 들어간다.
- **보존 기한(기본값, 설정 가능)**:
  - 대화형 입력·출력: 결과 전달 후 24시간(재배정·이어쓰기·구매자 재조회·중복 실행 비교에 필요한 최소). 구매자가 `x-binjari-retention: none`을 주면 스트리밍·즉시 응답에 한해 결과를 저장하지 않는다(입력은 작업 종료까지만).
  - 배치 입력 파일: 배치 종료 후 7일. 결과 파일: 생성 후 7일(S15).
  - 검증 비교: 중복 실행 결과는 비교 직후 버리고 점수·해시·길이만 남긴다. 카나리아는 우리 합성 데이터라 예외. 검증 표본으로 뽑힌 작업의 원 출력은 판정까지 최대 48시간 보존한다. `x-binjari-retention: none` 작업은 표본에서 빠진다(노드는 모른다, ARCHITECTURE 12절 D10).
  - 삭제는 주기 작업(retention)이 하고, 되돌릴 수 없으므로 설정값·테스트로 확인한다(S12).
  - 백업: 삭제된 콘텐츠의 암호문이 백업 보존 기간(S29에서 정함, 목표 7일)만큼 남는다 → 수용한 위험(키 없이는 못 읽음). 문서와 개인정보 안내에 적는다.
- **노드**: 작업 데이터는 메모리에만. 실행기 경로에 디스크 쓰기 코드가 없음을 정적 검사·통합 테스트로 확인(S22). llama-server는 프롬프트 로그·디스크 캐시·슬롯 저장을 끈다(S19). 크래시 덤프(WER)는 런타임 실행 파일에 대해 끄거나, 불가하면 수용한 위험으로 문서화(S22). 페이지 파일로 메모리가 디스크에 내려가는 것은 OS 동작이라 막지 않는다(수용, THREAT_MODEL).
- **전송**: 구매자 ↔ 서버, 서버 ↔ 에이전트 모두 TLS. 에이전트 ↔ llama-server는 127.0.0.1(평문, 같은 PC 안).
- **사람의 열람**: v0.1에는 콘텐츠 열람 기능이 없다. 운영자 검토 화면은 해시·점수·길이 중심(S13·S26).
- **외부 모델**: 외부 모델(Claude 등) 요청의 콘텐츠는 제공사로 간다. 우리 쪽에는 저장하지 않고(`external_usage`는 메타데이터만, S16), 구매자 문서에 제공사로 전달됨을 밝힌다. 제공사 보존 정책은 '확인 필요'(HUMAN_TODO 약관 검토).
- **노드 쪽에서 구매자 신원 숨김**: 오퍼에는 구매자 ID·키 정보를 넣지 않는다. 배치 결과에 노드 식별 정보를 넣지 않는다(S15).

## 검토한 대안
| 대안 | 장점 | 단점 | 버린 이유 |
|---|---|---|---|
| 서버에 콘텐츠를 전혀 저장하지 않음 | 가장 안전 | 선점 후 재배정·이어쓰기·배치·서버 재시작 후 이어하기가 불가 | 손님 우선(선점)과 배치가 사업의 핵심 |
| 종단 간 암호화(구매자 → 노드) | 서버도 못 읽음 | 서버 토큰 계산(ADR 0009)·검증 비교가 불가, 노드는 어차피 평문을 본다 | 이득이 작다 |
| 작업별 데이터 키(암호 파쇄) | 백업에서도 즉시 지울 수 있음 | 키 관리 복잡 | v0.1에는 과함. 재검토 조건에 둔다 |
| 보존 30일 | 디버깅·분쟁 대응 편함 | 데이터 노출 기간 증가 | 최소 보관 원칙 |

## 결과와 트레이드오프
- 쉬워지는 것: "프롬프트는 어디에 얼마나 남는가"에 한 표로 답할 수 있다([ARCHITECTURE 데이터 흐름 절](../ARCHITECTURE.md#6-데이터-흐름과-보존)).
- 어려워지는 것: 구매자가 24시간 뒤 결과를 다시 받을 수 없다. 분쟁 시 원문 증거가 없다(해시만).
- 손님 PC에서 처리되는 이상 '메모리에서 읽힐 위험'은 0이 아니다 → 민감하지 않은 작업만 받는다는 안내(구매자 문서)를 둔다. '신뢰 노드 전용' 선택지(`x-binjari-trusted-only` 같은 헤더)는 v0.1 범위 밖이다(MVP 비목표). 수요가 확인되면 S12 스케줄러 하드 조건으로 추가한다.

## 재검토 조건
- 기업 구매자가 데이터 처리 계약(DPA)·보존 0을 요구할 때(작업별 키 + 즉시 파쇄 검토).
- 개인정보보호 관련 법률 검토 결과가 나올 때.
- 백업 보존 기간이 30일 이상으로 늘어날 때.
