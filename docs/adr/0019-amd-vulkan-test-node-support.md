# 0019. AMD GPU는 llama.cpp Vulkan 빌드로 '시험 노드'까지만 지원한다

- 상태: 채택
- 날짜: 2026-10-10
- 차수: S03(러너 진행 중 사람의 결정으로 추가)

## 맥락
- 창업자가 지금 실기 확인에 쓸 수 있는 PC는 **AMD Radeon RX 5700 XT(8GB, RDNA1) 1대**뿐이다(2026-10-10 사람이 알림).
- 기존 설계는 v0.1을 NVIDIA 전용으로 잡았다. 런타임은 llama.cpp Windows CUDA 빌드(ADR 0004)이고, GPU 정보·VRAM·온도·전력·GPU UUID는 nvidia-smi로 읽는다(ARCHITECTURE 모듈 `gpu`, S19). AMD는 MVP 비목표였다. 이대로면 S18~S22 실기 확인 중 GPU가 들어가는 항목(선점 → VRAM 해제 SLO-2, 런타임 실행, 처리량 측정, 세션 0 동작)을 할 수 없다.
- PC방 GPU는 대부분 NVIDIA라는 가정(MVP 비목표 표, BUSINESS_CONTEXT 10절)은 그대로다. 매장 수익 작업의 기준 플랫폼을 바꿀 근거는 없다.
- 사람이 고른 방향(2026-10-10): "AMD를 시험용으로 지원". NVIDIA 우선은 유지한다.

## 결정
1. **런타임 백엔드 2종.** 런타임 릴리스(S09)에 `backend` 속성(`cuda` | `vulkan`)을 둔다. 운영 기본은 `cuda`이고, AMD 노드는 llama.cpp **Vulkan** 빌드를 같은 서명·검증 절차로 받는다. 버전 고정·실행 원칙(ADR 0004)은 똑같이 적용한다. ROCm/HIP 빌드는 쓰지 않는다. RDNA1(gfx1010)이 Windows HIP SDK 공식 지원 목록에 없는 것으로 알고 있고(S19에서 확인), Vulkan은 제조사와 무관하게 하나로 처리된다.
2. **GPU 인터페이스는 제조사별 구현.** 에이전트 `gpu` 모듈(S17 인터페이스, S19 구현)에 `nvidia`(nvidia-smi)와 `windows`(제조사 무관) 구현을 둔다. `windows` 구현은 GPU 목록·전체 VRAM을 DXGI 어댑터 정보로, **프로세스별 VRAM 사용량을 Windows 성능 카운터 `GPU Process Memory`(Dedicated Usage)로** 읽는다. 선점 뒤 'VRAM 해제 확인'(S18, SLO-2)은 AMD에서 이 카운터로 한다. NVIDIA에서는 nvidia-smi로 하고, 카운터는 교차 확인용으로 쓸 수 있다.
3. **온도·전력은 '모름'을 허용하되 시험 노드에서만.** AMD는 온도·전력을 읽는 표준 명령줄 도구가 없다(제조사 SDK 연동은 v0.1 범위 밖). AMD 노드는 `tempC`·`powerW`를 '모름'으로 보고하고, 사장님 화면의 전력·전기요금은 '측정 불가'로 표시한다. 대신 GPU 과열 보호는 하드웨어 자체 스로틀링에 맡긴다. 이 예외는 아래 4번의 시험 노드에만 적용한다. **GPU 목록·VRAM 읽기 실패는 지금처럼 멈춤**이다(ADR 0016은 약해지지 않는다).
4. **AMD(Vulkan) 노드는 v0.1에서 시험 노드.** 배정(S12)은 Vulkan 노드에 TCR 작업과 카나리아만 준다. 매장 검증 여부와 상관없이 CR 수익 작업은 주지 않는다. 검증(S13)과 카나리아 기준값은 **같은 백엔드끼리만** 비교한다. CUDA와 Vulkan의 출력 차이를 비결정성으로 오판하지 않기 위해서다.
5. **기기 지문.** AMD에는 NVIDIA GPU UUID에 해당하는 값이 없다. `fpStore`·`fpGlobal`의 원본은 디스플레이 어댑터의 PnP 장치 인스턴스 ID(PCI 공급사·장치·하위 시스템·위치)로 한다(S10·S17·S20에서 확정). 위협은 AGT-18과 같다. 클라이언트가 주장하는 값이고 사용자 권한으로 읽힌다.
6. **프로토콜(S19에서 변경, 프로토콜 해시 갱신).** `capabilities.gpus[]`에 `vendor`(`nvidia` | `amd` | `other`)를 추가하고, `computeCapability`는 NVIDIA에서만 필수로 한다. AMD는 `arch`(예: `gfx1010`)를 보고한다. `capabilities.runtime`에 `backend`를 추가한다. `status.gpus[]`의 `tempC`·`powerW`는 '모름'을 표현할 수 있게 바꾼다. 스키마 하나에서 TS·Go 양쪽 검증과 fixture를 같이 갱신한다(ADR 0017 규칙).
7. **0단계 데모(S04).** 데모는 Ollama 어댑터를 쓴다. AMD GPU를 Ollama가 가속하지 못하면 CPU로 돌아간다. 느려도 데모 흐름은 같다. `docs/DEMO_0.md`에 이 경우를 적는다.

## 검토한 대안
| 대안 | 장점 | 단점 | 버린 이유 |
|---|---|---|---|
| NVIDIA 전용 유지, 실기는 NVIDIA PC를 구한 뒤 | 범위 변화 없음 | 지금 가진 유일한 PC로 GPU 실기 확인을 전혀 못 한다. 선점·VRAM 해제(손님 보호의 핵심)를 실제 GPU에서 확인하는 시점이 미뤄진다 | 사람이 고르지 않음. 손님 보호 확인이 늦어지는 비용이 더 크다 |
| AMD를 NVIDIA와 동등하게 정식 지원(수익 작업 포함) | 매장 GPU 선택 폭 | 온도·전력에 제조사 SDK(cgo/DLL) 연동, 검증 기준 이원화, 처리량·비결정성 실측 두 배 | 1인 운영에 과함. 파일럿 매장 GPU 분포(K13)를 보고 다시 정한다 |
| ROCm/HIP 빌드 | AMD에서 더 빠를 수 있음 | RDNA1은 Windows HIP 지원 대상이 아님(확인 필요). 세대마다 지원이 갈린다 | Vulkan이 단순하고 넓다 |
| Vulkan 빌드를 NVIDIA에도 써서 백엔드 하나로 | 런타임 1종, 검증 기준 1종 | NVIDIA에서 CUDA보다 느리고 프롬프트 처리 성능이 떨어진다(S19 실측 전) | 수익을 내는 주 플랫폼의 성능을 희생한다. S19 bench가 차이가 작다고 보이면 재검토 |

## 결과와 트레이드오프
- 쉬워지는 것: 지금 가진 RX 5700 XT로 손님 감지 → 선점 → 프로세스 종료 → VRAM 해제(S18), 런타임 설치·실행·처리량(S19), 세션 0 동작(S22)을 실제로 확인할 수 있다. 단 Vulkan 경로 기준이다.
- 어려워지는 것: 런타임 아티팩트·GPU 구현·검증 기준이 백엔드별로 갈라진다. 테스트 행렬이 커진다(fixture·가짜 GPU 두 종류). CUDA 경로의 실기 확인(K1의 CUDA 부분, nvidia-smi 전력 K8)은 여전히 NVIDIA PC가 있어야 한다.
- AMD 실기 결과를 NVIDIA에 그대로 옮길 수 없다. 특히 VRAM 해제 시간과 세션 0 동작은 드라이버마다 다르다. 실기 보고에는 GPU·백엔드를 함께 적는다.
- 되돌리는 비용: 작다. Vulkan 노드는 수익 작업을 받지 않으므로 지원을 끊어도 원장·정산에 남는 것이 없다.

## 재검토 조건
- 파일럿 매장 GPU 중 NVIDIA가 아닌 비율이 20%를 넘을 때(ADR 0004와 같은 기준) → AMD 정식 지원(수익 작업·온도 읽기)을 새 ADR로 검토한다.
- S19 bench에서 NVIDIA의 Vulkan 처리량이 CUDA의 85% 이상일 때 → 백엔드를 Vulkan 하나로 합치는 것을 검토한다.
- Windows 성능 카운터로 프로세스별 VRAM을 신뢰성 있게 읽지 못할 때(S18·S19 실기) → AMD 노드의 VRAM 해제 확인을 '프로세스 종료 + 전체 사용량 감소'로 바꾸고 그 판단을 이 ADR에 기록한다.
